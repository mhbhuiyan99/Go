# Beego Filters & Middleware

Reference notes on Beego's global filter system: `web.InsertFilter`,
execution positions, `FilterChain`, and common middleware patterns (auth,
CORS, rate limiting, logging).

> **Scope note:** `04. Routing.md` already covers namespace-scoped
> middleware (`web.NSBefore` / `web.NSAfter`), which runs before/after
> routes *inside one namespace*. This note covers the separate, more
> powerful **global filter system** (`InsertFilter`) that Beego actually
> runs internally — `NSBefore`/`NSAfter` are a convenience layer built on
> top of it. Read that section first if you haven't; this picks up where
> it leaves off.

---

# Part 1 — Beginner

## 1. Why two middleware systems exist

- **`web.NSBefore` / `web.NSAfter`** (in `04. Routing.md`) — scoped to one
  namespace, simple, good for "run this before every route under `/api/v1`."
- **`web.InsertFilter`** — global, pattern-matched against *any* route
  (not tied to a namespace), with five distinct execution points instead
  of just "before" and "after." This is what you reach for when you need
  precision about *when* in the request lifecycle something runs, or when
  the concern isn't cleanly scoped to one namespace (e.g. access logging
  for the whole app).

Both ultimately register the same underlying `FilterFunc` type — namespace
filters are just a scoped shortcut over `InsertFilter`.

---

## 2. The `FilterFunc` signature

```go
type FilterFunc func(ctx *context.Context)
```

Every filter — namespace-level or global — is just a function taking the
request `*context.Context`. There's no `next()` call like Express/Koa
middleware; instead, Beego decides whether to continue based on **whether
the filter already wrote output** (see `WithReturnOnOutput` in §5).

```go
var LogFilter = func(ctx *context.Context) {
    log.Printf("%s %s", ctx.Input.Method(), ctx.Input.URL())
}
```

---

## 3. Registering a global filter

<cite index="34-1">`InsertFilter`'s parameters: pattern — string or regex to match against router rules, use `/*` to match all; pos — the execution point; filter — the filter function; and options.</cite>

```go
web.InsertFilter("/*", web.BeforeRouter, LogFilter)
```

```go
web.InsertFilter("/api/*", web.BeforeRouter, AuthFilter) // only /api/* routes
```

The pattern uses the same matching rules as `web.Router()`, so you can
scope a filter as tightly or loosely as a route pattern allows.

---

## 4. The five execution points

<cite index="34-1">web.BeforeStatic: before finding the static file. web.BeforeRouter: before finding router. web.BeforeExec: after finding router and before executing the matched Controller. web.AfterExec: after executing Controller. web.FinishRouter: after finishing router.</cite>

```
Request in
   │
   ▼
BeforeStatic   ← runs before Beego checks if this is a static file request
   │
   ▼
BeforeRouter   ← runs before route matching; session NOT yet initialized
   │
   ▼
   (route matched, session initialized)
   │
   ▼
BeforeExec     ← runs right before the controller method executes
   │
   ▼
   (controller method runs — your Get()/Post()/etc.)
   │
   ▼
AfterExec      ← runs right after the controller method finishes
   │
   ▼
FinishRouter   ← runs after the whole routing cycle completes
   │
   ▼
Response out
```

**Practical implications of each point:**

| Point | Use it for | Watch out for |
|---|---|---|
| `BeforeStatic` | Blocking/logging static asset requests specifically | Rarely used for API-only apps |
| `BeforeRouter` | Auth checks, IP blocking, global rate limiting | **Session is not yet available here** |
| `BeforeExec` | Session-dependent auth, per-route rate limiting | Runs after routing, so 404s never reach it |
| `AfterExec` | Response header injection, response-body logging | Controller already ran — too late to block execution |
| `FinishRouter` | Access logging, metrics, cleanup | Can't modify the response meaningfully anymore |

---

## 5. `WithReturnOnOutput` and `WithResetParams`

<cite index="32-1">`web.WithReturnOnOutput` sets whether, if there is already output before this filter is performed, execution should stop — the default behavior is to stop (return) once output exists.</cite>

```go
web.InsertFilter("/*", web.AfterExec, MetricsFilter, web.WithReturnOnOutput(false))
```

This matters because filters at the **same execution point** run in
registration order, and by default, once one filter writes output (e.g.
`ctx.Output.SetStatus` + a body), Beego stops running the rest at that
point. If you need multiple independent filters to *all* run regardless
(e.g. both a metrics filter and a logging filter at `AfterExec`), pass
`web.WithReturnOnOutput(false)` on each.

`web.WithResetParams` — <cite index="34-1">controls whether params are reset to their previous values after the filter completes</cite>, relevant if your filter mutates request params and you don't want that mutation to leak into the controller.

# Part 2 — Advanced

## 7. Auth filter (the canonical example)

```go
var AuthFilter = func(ctx *context.Context) {
    if strings.HasPrefix(ctx.Input.URL(), "/login") {
        return // skip auth for the login route itself
    }
    uid, ok := ctx.Input.Session("uid").(int)
    if !ok || uid == 0 {
        ctx.Output.SetStatus(401)
        ctx.Output.JSON(map[string]interface{}{
            "success": false,
            "message": "unauthorized",
        }, false, false)
        return
    }
}

web.InsertFilter("/api/*", web.BeforeExec, AuthFilter)
```

Registered at `BeforeExec`, not `BeforeRouter`, because it reads
`ctx.Input.Session(...)` — <cite index="13-1">filters which use session must be executed after `BeforeRouter`, because session is not initialized before that.</cite> This is the single most common filter-ordering bug: an auth filter silently failing to see session data because it was registered one step too early.

---

## 8. CORS filter

```go
var CORSFilter = func(ctx *context.Context) {
    ctx.Output.Header("Access-Control-Allow-Origin", "*")
    ctx.Output.Header("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS")
    ctx.Output.Header("Access-Control-Allow-Headers", "Content-Type,Authorization")
    if ctx.Input.Method() == "OPTIONS" {
        ctx.Output.SetStatus(204)
    }
}

web.InsertFilter("/*", web.BeforeRouter, CORSFilter)
```

Registered at `BeforeRouter` (not `BeforeExec`) deliberately — a preflight
`OPTIONS` request should get its `204` response before Beego even attempts
route matching against a real controller, since `OPTIONS` won't match any
of your `Get`/`Post`/etc. methods.

---

## 9. Built-in rate limiting filter

Beego ships a token-bucket rate limiter as a ready-made filter, so you
don't have to hand-roll one for the common case:

```go
import "github.com/beego/beego/v2/server/web/filter/ratelimit"

web.InsertFilter("/", web.BeforeRouter, ratelimit.NewLimiter())
```

<cite index="32-1">The token bucket algorithm is controlled by two parameters — capacity and rate. By default, capacity is 100 and the rate generates one token every ten milliseconds.</cite>

For per-endpoint (rather than global) rate limiting: <cite index="32-1">if the limit should be relative to a particular API/session, use `WithSessionKey` and register the filter at `BeforeExec` instead of `BeforeRouter`, since the route needs to already be known.</cite>

```go
web.InsertFilter("/api/expensive", web.BeforeExec, ratelimit.NewLimiter(
    ratelimit.WithSessionKey(true),
))
```

For **distributed** rate limiting across multiple app instances (this
built-in limiter is in-process/per-instance, same limitation as the
`memory` cache provider), fall back to the Redis-backed counter pattern
described in the cache note's Part 3 Q&A.

## 10. FilterChain — composable, Express-style middleware

<cite index="15-1">Beego also supports `InsertFilterChain`, which wraps filters as a chain where the last filter in the chain actually serves the request</cite> — closer to standard Go `http.Handler` middleware composition than the position-based `InsertFilter` model.

```go
fb := &prometheus.FilterChainBuilder{}
web.InsertFilterChain("/*", fb.FilterChain)
```

Write your own:

```go
func MyChainMiddleware(next web.FilterFunc) web.FilterFunc {
    return func(ctx *context.Context) {
        start := time.Now()
        next(ctx) // call through to the next link in the chain
        log.Printf("took %s", time.Since(start))
    }
}

web.InsertFilterChain("/*", MyChainMiddleware)
```

**When to reach for `FilterChain` instead of `InsertFilter`:** when you
want to wrap behavior *around* the rest of the pipeline (timing,
before-and-after logic in one function) rather than picking a single fixed
execution point — it composes more naturally for things like request
timing, panic recovery, or wrapping third-party instrumentation (this is
how Beego's own `prometheus` metrics filter is built).

---

## 11. Panic recovery as a filter

A JSON API should never let a panic bubble up into Beego's default HTML
error page. A recovery filter at `AfterExec` (or wrapped as a `FilterChain`
around the whole pipeline) catches it:

```go
func RecoveryFilterChain(next web.FilterFunc) web.FilterFunc {
    return func(ctx *context.Context) {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("panic recovered: %v", r)
                ctx.Output.SetStatus(500)
                ctx.Output.JSON(map[string]interface{}{
                    "success": false,
                    "message": "internal server error",
                }, false, false)
            }
        }()
        next(ctx)
    }
}

web.InsertFilterChain("/*", RecoveryFilterChain)
```

This is the fix for the "API sometimes returns HTML instead of JSON on
errors" symptom — without a recovery layer, an unhandled panic anywhere in
a controller falls through to Beego's default error handling.

---

## 12. Filter execution order across multiple filters at the same point

When several filters share one execution point (e.g. multiple `BeforeRouter`
filters), they run in **registration order** — the order you call
`InsertFilter` in your `init()`/`main()`. This matters when one filter
depends on another having already run (e.g. a request-ID filter that must
run before a logging filter that reads that request ID). Keep filter
registration centralized (e.g. one `filters.go` with all `InsertFilter`
calls in a deliberate order) rather than scattered across multiple files,
so the ordering is visible and intentional rather than accidental.

# Part 3 — Use-Case Q&A

**Q: You wrote an auth filter, but requests with no session still get through. What's the first thing to check?**

Whether it's registered at `BeforeRouter` instead of `BeforeExec`. Session
data isn't initialized until after `BeforeRouter` runs, so a filter reading
`ctx.Input.Session(...)` at `BeforeRouter` will always see empty/missing
session data — it's not that the filter isn't running, it's that it's
running too early to see what it's checking for.

---

**Q: Your CORS preflight (`OPTIONS`) requests are getting 404s instead of the expected 204. Why?**

The CORS filter is likely registered at `BeforeExec` instead of
`BeforeRouter`. `OPTIONS` requests don't match any `Get`/`Post`/etc.
controller method, so if the filter only runs *after* routing succeeds, it
never runs for a route that has no `Options` handler — routing already
failed with a 404 by that point. Registering at `BeforeRouter` lets the
filter intercept and respond before route matching happens.

---

**Q: You have both a metrics filter and a logging filter registered at `AfterExec`, but only the metrics filter seems to run. Why?**

The metrics filter almost certainly writes output (a status code / body)
without `web.WithReturnOnOutput(false)` set. By default, once one filter
at a given execution point produces output, Beego stops running further
filters at that same point. Pass `WithReturnOnOutput(false)` on filters
that need to coexist with others at the same point.

---

**Q: When would you reach for `InsertFilterChain` instead of a plain `InsertFilter`?**

When the logic naturally wraps *around* the rest of the request (timing,
panic recovery, before-and-after in one function) rather than fitting one
fixed point in the pipeline. `InsertFilter` is best for "run this one
check at this one moment"; `FilterChain` is best for "wrap everything
downstream with this behavior," which is why Beego's own instrumentation
filters (Prometheus metrics) are built as chains.

---

**Q: Your built-in rate limiter works fine locally but doesn't actually limit anything once you scale to 3 app instances behind a load balancer. Why?**

The token-bucket `ratelimit` filter is per-process/in-memory, same as the
`memory` cache provider — each of the 3 instances tracks its own bucket
independently, so a client can get 3× the intended limit by having
requests distributed across instances. For a real distributed limit, back
the counter with `redis` (atomic `Incr` shared across all instances)
instead of relying on the built-in in-process limiter.

---

**Q: Where should panic recovery live — inside every controller, or somewhere else?**

A single `FilterChain`-based recovery wrapper registered once for `/*`,
not `recover()` calls duplicated in every controller method. The whole
point of filters is that cross-cutting concerns (recovery, auth, CORS,
logging) live in one place instead of being copy-pasted — and repeated
per-controller `recover()` blocks are exactly the kind of thing that gets
forgotten in a new controller someone adds six months from now.

---

**Q: You need a request-ID filter that a later logging filter depends on. How do you guarantee it runs first?**

Filters at the same execution point run in registration order, so register
the request-ID filter's `InsertFilter` call before the logging filter's —
and keep all filter registrations together in one place (e.g. a single
`filters.go` `init()`) so that ordering dependency is visible in one spot,
rather than depending on Go's file-processing order across multiple files,
which is fragile and easy to break by accident.

---

**Q: A route-specific rate limit only needs to apply to one expensive endpoint, not the whole API. How do you scope it?**

Two levers: the `pattern` argument to `InsertFilter` (e.g.
`"/api/expensive"` instead of `"/*"`), and choosing `BeforeExec` +
`ratelimit.WithSessionKey(true)` if the limit should key off the matched
route/session rather than being a single global bucket. Don't reach for a
global `/*` filter with internal per-route branching logic when the
pattern argument already does that scoping for you declaratively.
