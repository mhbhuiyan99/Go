# Beego Request Lifecycle — Notes

Reference notes on the complete path a request takes through Beego, from
the socket to the rendered response — how routing, filters, and the
controller lifecycle fit together as one pipeline.

> **Scope note:** `04. Routing.md` covers route *matching rules*,
> `05. Controllers.md` covers controller *usage*, and the Filters &
> Middleware note covers the 5 filter execution points in isolation. This
> note is the connective tissue — the full end-to-end sequence showing
> exactly where routing, filters, and controller hooks (`Init`, `Prepare`,
> `Render`, `Finish`, XSRF checks) all sit relative to each other in one
> request.

---

# Part 1 — Beginner

## 1. The pipeline at a glance

Every request moves through the same ordered pipeline, regardless of
which controller ultimately handles it:

```
Request arrives on the listen port (default :8080)
   │
   ▼
Context initialized
   │
   ▼
BeforeRouter filter runs (if registered)
   │
   ▼
Static file check — does the URL match a StaticDir prefix?
   │
   ├── YES → served directly via http.ServeFile, pipeline ends here
   │
   ▼ NO
Session initialized (if session module enabled)
   │
   ▼
AfterStatic filter runs (if registered)
   │
   ▼
Route matching, in this fixed order:
   1. Fixed routes (exact/pattern match via web.Router)
   2. Regex routes (in registration order)
   3. Auto router (if enabled)
   │
   ├── NO MATCH at any stage → 404
   │
   ▼ MATCH FOUND
BeforeExec filter runs (if registered)
   │
   ▼
Controller.Init() — basic setup, don't override lightly
   │
   ▼
XSRF check (XsrfToken, and CheckXSRFCookie if POST + XSRF enabled)
   │
   ▼
Controller.Prepare() — your custom pre-request setup
   │
   ▼
Verb method runs — Get() / Post() / Put() / etc. (your actual logic)
   │
   ▼
Controller.Render() — if no output was written manually, renders the template
   │
   ▼
Controller.Finish() — your custom cleanup/resource release
   │
   ▼
AfterExec filter runs (if registered)
   │
   ▼
Destructor — releases data allocated in Init
   │
   ▼
Supervisor/monitoring logging (if enabled, default port :8088)
   │
   ▼
Response sent
```

This is the real shape of the "Request Lifecycle" diagram — the numbered
steps below map onto Beego's own 21-step description of this same flow.

---

## 2. Server start and context initialization

`main.go`'s `web.Run()` starts listening (default port `8080`). For each
incoming request, Beego creates a `*context.Context` — this is the object
threaded through the entire pipeline (`ctx.Input`, `ctx.Output`), and it's
the same `*context.Context` your filters and `c.Ctx` inside controllers
both reference.

---

## 3. `BeforeRouter` — the earliest filter hook

Covered in depth in the Filters & Middleware note. The key lifecycle fact
worth repeating here: this runs **before** static file handling and
**before** session initialization — so a `BeforeRouter` filter can
intercept literally any request, including ones that would otherwise be
served as a static file, but it cannot read session data yet.

---

## 4. Static file handling

If the requested URL matches a configured `StaticDir` prefix, Beego serves
the file directly (via Go's standard `http.ServeFile`) and the pipeline
**ends there** — it never reaches routing or any controller. This is why
static asset requests don't trigger `BeforeExec`/`AfterExec` or any
controller lifecycle hooks at all.

---

## 5. Session initialization and `AfterStatic`

For non-static requests, if the session module is enabled, session state
is initialized at this point — **after** static-file handling, **before**
routing. `AfterStatic` is the filter position designed for
session-dependent logic that needs to run early but after this
initialization — this is the underlying reason the Filters note tells you
to avoid session access at `BeforeRouter`.

---

## 6. Route resolution order

Beego tries route-matching strategies in a fixed priority order, falling
through to the next only if the previous finds nothing:

1. **Fixed routes** — exact/pattern matches registered via `web.Router()`.
2. **Regex routes** — tried in the order you registered them, so
   registration order matters if patterns could overlap.
3. **Auto router** — reflection-based fallback, only tried if enabled and
   nothing above matched.

If none match, it's a `404`.

---

## 7. The controller lifecycle hooks, in order

Once a controller is matched: `BeforeExec` filter → `Init()` → XSRF check
→ `Prepare()` → your verb method (`Get`/`Post`/etc.) → `Render()` →
`Finish()` → `AfterExec` filter → destructor.

- **`Init()`** — sets up `bee.Controller`'s own internals; overriding it is
  discouraged since you can break base functionality the framework relies on.
- **`Prepare()`** — the intended hook for *your* pre-request setup (auth
  checks scoped to one controller, loading shared data for all its
  actions, etc.) — this is the safe override point, not `Init()`.
- **`Render()`** — only actually renders a template if your verb method
  didn't already write output manually (e.g. via `ServeJSON()`).
- **`Finish()`** — the intended hook for *your* cleanup (releasing
  anything set up in `Prepare`).

# Part 2 — Advanced

## 9. Common misconceptions about the pipeline

A few points worth stating explicitly, since they're easy to get wrong
when picturing the pipeline from a simplified diagram or mental model:

1. **Static file handling and the `AfterStatic` filter are not parallel
   branches — they're sequential, and static requests exit early.** The
   real order is: static-file check first — if it matches, the request is
   served and the pipeline ends *right there*. Only for **non-static**
   requests does the flow continue on to session init, then the
   `AfterStatic` filter. It's a common mistake to assume both paths always
   run for every request; a matched static file never reaches
   `AfterStatic`, routing, or any controller hook at all.

2. **The "admin/monitoring" step isn't a conditional UI branch — it's a
   logging/metrics hook every request passes through.** Every request path
   (matched, filtered-out, or 404) funnels into this same final step — if
   Beego's supervisor module is enabled (default port `8088`), the
   request's stats (QPS, timing, URL) are logged to it. It's easy to
   picture this as "if admin enabled, go to admin dashboard," but it's
   really a passive logging step at the end of *every* request's journey,
   not a branch that redirects some requests differently.

3. **The XSRF check isn't one generic "check XSRF" step** — it's two
   distinct things in sequence: `XsrfToken()` is called if XSRF protection
   is enabled at all, and `CheckXSRFCookie()` is called specifically
   **only when the request is a POST**. A GET request with XSRF enabled
   gets a token generated/available but isn't checked against one, since
   GET shouldn't be mutating anything in the first place.

These distinctions matter once you're actually debugging why a filter or
hook didn't fire when you expected.

---

## 10. Short-circuiting: what happens when a filter writes output

This is the mechanic that makes several "if X then jump to Y" steps in
the lifecycle make sense as a coherent design, not arbitrary branches:
**at almost every filter point, if the filter already wrote response
output (status code + body), Beego skips the rest of the normal pipeline
and jumps straight to the final logging/supervisor step.**

Concretely: if your `BeforeRouter` auth filter rejects a request and
writes a `401` response, Beego doesn't then go on to try static file
matching, routing, or any controller hooks — it goes straight to the end
(supervisor logging), because there's already a response to send. This is
the same `WithReturnOnOutput` mechanic from the Filters & Middleware note,
just now visible as part of the full lifecycle rather than one isolated
filter behavior.

**Practical implication:** a filter that accidentally writes *any* output
(even a stray debug print through `ctx.Output`) will silently truncate the
rest of the pipeline for that request — including skipping controller
execution entirely. This is a real, hard-to-spot bug class: "my controller
method never runs" traced back to a filter upstream writing output it
didn't intend to.

---

## 11. XSRF protection in detail

```go
web.BConfig.WebConfig.EnableXSRF = true
web.BConfig.WebConfig.XSRFKey = "your-secret-key"
web.BConfig.WebConfig.XSRFExpire = 3600
```

With XSRF enabled: `XsrfToken()` runs for every request to make a token
available (e.g. for embedding in a rendered form), while
`CheckXSRFCookie()` runs and actually **validates** the token only for
POST requests — the token can be provided in the request header `X-Xsrftoken` or `X-CsrfToken`, or in a form field named `_xsrf`. A POST that fails this check gets rejected before your controller's `Prepare()` or verb method ever runs — this is enforced at the controller-lifecycle level, not something your own code needs to check manually once enabled.

For a **JSON API** (no server-rendered forms), Beego's cookie-based XSRF
protection is usually not the right tool — it's designed for
traditional form-based apps. API auth is typically handled instead via a
`BeforeExec`/`BeforeRouter` auth filter (see the Filters & Middleware
note) checking a bearer token, not XSRF cookies.

---

## 12. `Prepare()` vs a `BeforeExec` filter — which one for auth?

Both run before your controller logic, so it's a common point of
confusion:

- **`BeforeExec` filter** — global or pattern-scoped, applies across
  *multiple controllers* matching the pattern. Right choice for auth that
  applies broadly (e.g. "everything under `/admin/*`").
- **`Prepare()`** — scoped to *one controller* (and all its actions,
  since every verb method shares the same `Prepare()`). Right choice for
  setup specific to that controller alone — e.g. loading a resource by ID
  from the URL param once, so every verb method (`Get`/`Put`/`Delete`) on
  that resource can reuse it without repeating the lookup.

Using `Prepare()` for cross-cutting auth (duplicated in every controller)
recreates the exact problem filters exist to solve — see the Filters &
Middleware note's Q&A on where auth logic belongs.

---

## 13. The supervisor/monitoring module

```go
web.BConfig.Listen.EnableAdmin = true
web.BConfig.Listen.AdminAddr = "localhost"
web.BConfig.Listen.AdminPort = 8088
```

When enabled, every request funnels its stats (QPS, response time,
matched URL) into this module at the very end of the lifecycle — visible
via the admin port's own endpoints (e.g. `/qps`, `/prof`). This runs
regardless of whether the request succeeded, hit a filter short-circuit,
or 404'd — it's the universal final step every single request path
converges on.

> ⚠️ The admin/supervisor port exposes internal metrics and profiling
> endpoints — bind it to `localhost` (not `0.0.0.0`) or put it behind
> network-level access control in production; it's not meant to be
> internet-facing.

# Part 3 — Use-Case Q&A

**Q: A request to a static asset path is triggering your `AfterStatic` filter unexpectedly slowly, and you assumed static files always go through the full pipeline. Is that assumption right?**

No — a matched static file request is served directly via `http.ServeFile`
and the pipeline **ends there**; it doesn't continue on to session init,
`AfterStatic`, routing, or any controller hooks. If you're seeing
`AfterStatic` fire for what you thought was a static request, the URL
likely *didn't* actually match your configured `StaticDir` prefix and fell
through to the normal non-static path instead — worth double-checking the
prefix configuration rather than assuming the pipeline architecture is
different from documented.

---

**Q: Your controller method never seems to run, but you don't see a 404 either. Where do you look?**

A filter upstream (`BeforeRouter`, `BeforeExec`, or even `AfterStatic`)
that's accidentally writing output. Once any filter writes a response
(even unintentionally, e.g. a stray `ctx.Output.Body(...)` left in for
debugging), Beego short-circuits the rest of the pipeline straight to the
final logging step — your controller's `Init`/`Prepare`/verb method never
runs, and there's no error or 404, just a response that came from
somewhere earlier than you expected. Check filters registered on that
route's pattern first.

---

**Q: You need to load a resource (e.g. by `:id` param) once and have it available to `Get`, `Put`, and `Delete` on the same controller. `Init()` or `Prepare()`?**

`Prepare()` — `Init()` sets up the framework's own controller internals
and overriding it risks breaking base functionality. `Prepare()` is the
designated hook for your own per-request setup, and since it runs once
before whichever verb method ends up executing, it's exactly the right
place for logic shared across all of that controller's actions.

---

**Q: You enabled XSRF protection and a GET request to a form page works fine, but you're confused about when the token is actually validated.**

`XsrfToken()` runs on every request when XSRF is enabled (making a token
available, e.g. to embed in a form) — but `CheckXSRFCookie()`, the actual
*validation* step, only runs for POST requests. GET requests generate/expose
a token but aren't checked against one, which makes sense since GET
shouldn't be performing the mutating action XSRF protection guards
against in the first place.

---

**Q: Should you use Beego's built-in XSRF protection for a pure JSON REST API?**

Generally no — XSRF/CSRF cookie protection is designed around
browser-rendered forms with session cookies; a stateless JSON API
typically authenticates via bearer tokens instead, checked in an auth
filter (`BeforeExec`/`BeforeRouter`), which is a completely different
threat model. Enabling XSRF on a token-authenticated API usually just adds
friction without adding real protection, since the attack XSRF defends
against (a browser automatically attaching cookies to a forged
cross-site request) doesn't apply the same way to bearer-token auth.

---

**Q: Two different controllers both need "check user is authenticated" logic. Where should that live — `Prepare()` in each, or somewhere else?**

A `BeforeExec` filter scoped to both controllers' route pattern (or a
broader one), not duplicated `Prepare()` implementations. `Prepare()` is
correctly scoped to one controller's own setup; cross-cutting concerns
shared across multiple controllers are exactly what the filter system
(not controller hooks) exists to centralize — see the Filters &
Middleware note.

---

**Q: You want per-endpoint request timing/metrics without touching every controller. What's already built into Beego for this, before reaching for a custom filter?**

The supervisor/monitoring module (`EnableAdmin`) — every request,
regardless of outcome, funnels its stats into it as the final step of the
lifecycle. For anything beyond what it exposes (QPS, timing, matched URL),
a custom `FinishRouter` filter or `FilterChain` wrapper is the next step
up, but check whether the built-in module already covers your need before
building custom instrumentation.
