# Beego Request & Response Lifecycle

Reference notes on the complete path a request takes through Beego, from
the socket to the rendered response — how routing, filters, and the
controller lifecycle fit together as one pipeline.

> **Scope note:** `04. Routing.md` covers route *matching rules*,
> `05. Controllers.md` covers controller *usage*, and the `07. Filters &
> Middleware.md` note covers the 5 filter execution points in isolation. This
> note is the connective tissue — the full end-to-end sequence showing
> exactly where routing, filters, and controller hooks (`Init`, `Prepare`,
> `Render`, `Finish`, XSRF checks) all sit relative to each other in one
> request.

---

# Part 1 — Beginner

## 1. Request arrives

Every request starts the same way: it hits the port Beego is listening on
(default `:8080`, started by `web.Run()` in `main.go`). From here on, every
request — whatever URL, whatever verb — moves through the same ordered
pipeline before a response goes back.

---

## 2. Context is created

For each incoming request, Beego creates one `*context.Context` object.
This is the object threaded through the *entire* pipeline — it's the same
object your filters receive as an argument, and the same one your
controller accesses via `c.Ctx` (`c.Ctx.Input` for reading the request,
`c.Ctx.Output` for writing the response). Nothing else happens until this
exists.

---

## 3. Filters run at set points

Beego lets you hook custom logic in at specific points in the pipeline —
these are called filters (covered in full in the Filters & Middleware
note). For now, the only thing to know at the beginner level: filters can
run *before* routing happens and *after* a controller finishes, and if a
filter writes a response itself, the request can end early without ever
reaching a controller. The exact mechanics of that are an advanced topic
(§12 in Part 2) — just know filters exist as hook points in this pipeline.

---

## 4. Static file check

Before routing to a controller, Beego checks whether the URL matches a
configured static file directory (e.g. `/static/*`). If it does, the file
is served directly and the pipeline ends there — no controller, no
routing logic, nothing further runs. If it doesn't match, the request
continues on to routing.

---

## 5. Routing

Beego matches the request's URL against your registered routes to decide
which controller (and which method on it) should handle the request. At
the beginner level: you register routes with `web.Router("/path",
&SomeController{})`, and Beego calls the method matching the HTTP verb
(`Get` for GET, `Post` for POST, etc.) — the same rules covered in
`04. Routing.md`. If nothing matches, the request ends in a `404`.

There's more nuance to *how* Beego searches for a match (several
strategies, tried in order) — that's covered as an advanced topic in §11.

---

## 6. Controller execution

Once a route matches, the controller's lifecycle runs — this is the part
worth knowing in detail, since it's where your actual application code
lives:

```
BeforeExec filter (if registered)
   │
   ▼
Init()             — controller's own setup; don't override lightly
   │
   ▼
Prepare()          — YOUR pre-request setup goes here
   │
   ▼
Get() / Post() / Put() / Delete() / etc.   — YOUR actual request-handling logic
   │
   ▼
Render()           — renders a template, but only if you didn't already
   │                 write output manually (e.g. via ServeJSON())
   ▼
Finish()           — YOUR cleanup goes here
   │
   ▼
AfterExec filter (if registered)
```

- **`Init()`** — framework-level setup. Overriding it is discouraged since
  you can break base functionality the rest of the lifecycle depends on.
- **`Prepare()`** — the hook meant for *your* code: things that should run
  before every action on this controller (e.g. loading a resource once so
  `Get`/`Put`/`Delete` can all reuse it).
- **Your verb method** — the actual logic: read the request, do the work,
  write the response.
- **`Render()`** — only kicks in if your verb method didn't already
  produce output itself.
- **`Finish()`** — the hook meant for *your* cleanup, paired with
  `Prepare()`.

---

## 7. Response

However the response was produced — `ServeJSON()`/`ServeXML()` called
directly in your verb method, or a template rendered via `Render()` — it
goes back out through the same `*context.Context` from step 2, and the
request is done.

# Part 2 — Advanced

## 9. The full pipeline, in order

With the basics from Part 1 in place, here's the complete sequence,
including the pieces that were simplified above:

```
Request arrives on the listen port (default :8080)
   │
   ▼
Context initialized
   │
   ▼
BeforeRouter filter runs (if registered)
   │
   ▼
Static file check — does the URL match a StaticDir prefix?
   │
   ├── YES → served directly via http.ServeFile, pipeline ends here
   │
   ▼ NO
Session initialized (if session module enabled)
   │
   ▼
AfterStatic filter runs (if registered)
   │
   ▼
Route matching, in this fixed order:
   1. Fixed routes (exact/pattern match via web.Router)
   2. Regex routes (in registration order)
   3. Auto router (if enabled)
   │
   ├── NO MATCH at any stage → 404
   │
   ▼ MATCH FOUND
BeforeExec filter runs (if registered)
   │
   ▼
Controller.Init()
   │
   ▼
XSRF check (XsrfToken, and CheckXSRFCookie if POST + XSRF enabled)
   │
   ▼
Controller.Prepare()
   │
   ▼
Verb method runs — Get() / Post() / Put() / etc.
   │
   ▼
Controller.Render()
   │
   ▼
Controller.Finish()
   │
   ▼
AfterExec filter runs (if registered)
   │
   ▼
Destructor — releases data allocated in Init
   │
   ▼
Supervisor/monitoring logging (if enabled, default port :8088)
   │
   ▼
Response sent
```

This maps onto Beego's own documented 21-step lifecycle. The rest of this
part walks through everything here that wasn't covered in Part 1.

---

## 10. Static file handling and session initialization, precisely

Two details worth being exact about, since they're easy to get backwards:

1. **Static files exit the pipeline immediately** — a matched static
   request is served via `http.ServeFile` and never reaches session
   initialization, `AfterStatic`, routing, or any controller hook at all.
   It is *not* a parallel path that runs alongside the normal flow; it's
   an early exit.
2. **Session initialization sits between the static-file check and
   `AfterStatic`** — so for non-static requests, session state exists
   *after* this point but did not exist during `BeforeRouter`. This is the
   underlying reason a `BeforeRouter` filter can't reliably read session
   data (see the Filters & Middleware note) while an `AfterStatic` or
   `BeforeExec` filter can.

---

## 11. Route resolution order, in full

Beego tries route-matching strategies in a fixed priority order, falling
through to the next only if the previous finds nothing:

1. **Fixed routes** — exact/pattern matches registered via `web.Router()`.
2. **Regex routes** — tried in the order you registered them, so
   registration order matters if patterns could overlap.
3. **Auto router** — reflection-based fallback (`web.AutoRouter(...)`),
   only tried if enabled and nothing above matched. Beego reflects over
   the controller's methods and exposes them at
   `/controllername/methodname` automatically, with no explicit `Router()`
   call needed — convenient, but it means every exported method becomes
   reachable unless deliberately excluded (see `04. Routing.md`'s Q&A on
   why explicit routing is usually preferred for public APIs).

If none of the three match, it's a `404`.

---

## 12. Filter short-circuiting: what happens when a filter writes output

This is the mechanic that makes several "if X then jump to Y" branches in
the full pipeline (§9) coherent rather than arbitrary:
**at almost every filter point, if the filter already wrote response
output (status code + body), Beego skips the rest of the normal pipeline
and jumps straight to the final logging/supervisor step.**

Concretely: if a `BeforeRouter` auth filter rejects a request and writes a
`401` response, Beego doesn't then go on to try static file matching,
routing, or any controller hooks — it goes straight to the end (supervisor
logging), because there's already a response to send. This is the
`WithReturnOnOutput` mechanic from the Filters & Middleware note, visible
here as part of the full lifecycle rather than one isolated filter's
behavior.

**Practical implication:** a filter that accidentally writes *any* output
(even a stray debug write through `ctx.Output`) will silently truncate the
rest of the pipeline for that request — including skipping controller
execution entirely. This is a real, hard-to-spot bug class: "my controller
method never runs" traced back to a filter upstream writing output it
didn't intend to.

---

## 13. XSRF protection in detail

```go
web.BConfig.WebConfig.EnableXSRF = true
web.BConfig.WebConfig.XSRFKey = "your-secret-key"
web.BConfig.WebConfig.XSRFExpire = 3600
```

With XSRF enabled, it isn't one generic check — it's two distinct steps:
`XsrfToken()` runs on **every** request to make a token available (e.g.
for embedding in a rendered form), while `CheckXSRFCookie()` runs and
actually **validates** the token, but only for **POST** requests — the
token can be provided in the request header `X-Xsrftoken` or `X-CsrfToken`,
or in a form field named `_xsrf`. A POST that fails this check gets
rejected before your controller's `Prepare()` or verb method ever runs —
enforced at the controller-lifecycle level, not something your own code
needs to check manually once enabled. A GET request generates/exposes a
token but isn't checked against one, since GET shouldn't be performing a
mutating action in the first place.

For a **JSON API** (no server-rendered forms), Beego's cookie-based XSRF
protection is usually not the right tool — it's designed for
traditional form-based apps. API auth is typically handled instead via a
`BeforeExec`/`BeforeRouter` auth filter (see the Filters & Middleware
note) checking a bearer token, not XSRF cookies.

---

## 14. `Prepare()` vs a `BeforeExec` filter — which one for auth?

Both run before your controller logic, so it's a common point of
confusion:

- **`BeforeExec` filter** — global or pattern-scoped, applies across
  *multiple controllers* matching the pattern. Right choice for auth that
  applies broadly (e.g. "everything under `/admin/*`").
- **`Prepare()`** — scoped to *one controller* (and all its actions,
  since every verb method shares the same `Prepare()`). Right choice for
  setup specific to that controller alone — e.g. loading a resource by ID
  from the URL param once, so every verb method (`Get`/`Put`/`Delete`) on
  that resource can reuse it without repeating the lookup.

Using `Prepare()` for cross-cutting auth (duplicated in every controller)
recreates the exact problem filters exist to solve — see the Filters &
Middleware note's Q&A on where auth logic belongs.

---

## 15. The supervisor/monitoring module

```go
web.BConfig.Listen.EnableAdmin = true
web.BConfig.Listen.AdminAddr = "localhost"
web.BConfig.Listen.AdminPort = 8088
```

When enabled, every request funnels its stats (QPS, response time,
matched URL) into this module as the final step of the pipeline (§9) —
visible via the admin port's own endpoints (e.g. `/qps`, `/prof`). This
runs regardless of whether the request succeeded, hit a filter
short-circuit, or 404'd — it's the universal final step every single
request path converges on, not a conditional branch some requests take
and others don't.

> ⚠️ The admin/supervisor port exposes internal metrics and profiling
> endpoints — bind it to `localhost` (not `0.0.0.0`) or put it behind
> network-level access control in production; it's not meant to be
> internet-facing.

---

## 16. `FinishRouter` — the last filter position

`FinishRouter` (introduced in the Filters & Middleware note's execution
points) is the filter position that runs after the entire routing cycle
completes — after `AfterExec`, after the destructor, right before the
supervisor logging step in §9's diagram. It's the right place for:
access logging, metrics collection, or any cleanup that needs to see the
*final* state of the response regardless of which path the request took
to get there (matched controller, filter short-circuit, or 404) — unlike
`AfterExec`, which only runs if a controller actually executed.

# Part 3 — Use-Case Q&A

**Q: A request to a static asset path is triggering your `AfterStatic` filter unexpectedly, and you assumed static files always go through the full pipeline. Is that assumption right?**

No — a matched static file request is served directly via `http.ServeFile`
and the pipeline **ends there**; it doesn't continue on to session init,
`AfterStatic`, routing, or any controller hooks. If you're seeing
`AfterStatic` fire for what you thought was a static request, the URL
likely *didn't* actually match your configured `StaticDir` prefix and fell
through to the normal non-static path instead — worth double-checking the
prefix configuration rather than assuming the pipeline architecture is
different from documented.

---

**Q: Your controller method never seems to run, but you don't see a 404 either. Where do you look?**

A filter upstream (`BeforeRouter`, `BeforeExec`, or even `AfterStatic`)
that's accidentally writing output. Once any filter writes a response
(even unintentionally, e.g. a stray debug write left in through
`ctx.Output`), Beego short-circuits the rest of the pipeline straight to
the final logging step — your controller's `Init`/`Prepare`/verb method
never runs, and there's no error or 404, just a response that came from
somewhere earlier than you expected. Check filters registered on that
route's pattern first.

---

**Q: You need to load a resource (e.g. by `:id` param) once and have it available to `Get`, `Put`, and `Delete` on the same controller. `Init()` or `Prepare()`?**

`Prepare()` — `Init()` sets up the framework's own controller internals
and overriding it risks breaking base functionality. `Prepare()` is the
designated hook for your own per-request setup, and since it runs once
before whichever verb method ends up executing, it's exactly the right
place for logic shared across all of that controller's actions.

---

**Q: You enabled XSRF protection and a GET request to a form page works fine, but you're confused about when the token is actually validated.**

`XsrfToken()` runs on every request when XSRF is enabled (making a token
available, e.g. to embed in a form) — but `CheckXSRFCookie()`, the actual
*validation* step, only runs for POST requests. GET requests generate/expose
a token but aren't checked against one, which makes sense since GET
shouldn't be performing the mutating action XSRF protection guards
against in the first place.

---

**Q: Should you use Beego's built-in XSRF protection for a pure JSON REST API?**

Generally no — XSRF/CSRF cookie protection is designed around
browser-rendered forms with session cookies; a stateless JSON API
typically authenticates via bearer tokens instead, checked in an auth
filter (`BeforeExec`/`BeforeRouter`), which is a completely different
threat model. Enabling XSRF on a token-authenticated API usually just adds
friction without adding real protection, since the attack XSRF defends
against (a browser automatically attaching cookies to a forged
cross-site request) doesn't apply the same way to bearer-token auth.

---

**Q: Two different controllers both need "check user is authenticated" logic. Where should that live — `Prepare()` in each, or somewhere else?**

A `BeforeExec` filter scoped to both controllers' route pattern (or a
broader one), not duplicated `Prepare()` implementations. `Prepare()` is
correctly scoped to one controller's own setup; cross-cutting concerns
shared across multiple controllers are exactly what the filter system
(not controller hooks) exists to centralize — see the Filters &
Middleware note.

---

**Q: You want per-endpoint request timing/metrics without touching every controller. What's already built into Beego for this, before reaching for a custom filter?**

The supervisor/monitoring module (`EnableAdmin`) — every request,
regardless of outcome, funnels its stats into it as the final step of the
lifecycle. For anything beyond what it exposes (QPS, timing, matched URL),
a custom `FinishRouter` filter is the next step up, since it's the one
position guaranteed to run for every request path (matched, short-circuited,
or 404) — but check whether the built-in module already covers your need
before building custom instrumentation.

---

**Q: Why does Beego try fixed routes, then regex routes, then the auto router — in that specific order — instead of some other order?**

Fixed routes are the most explicit and specific, so they're checked first
to guarantee an exact, deliberately-registered match always wins.
Regex routes are more general (a pattern could technically overlap with a
fixed route), so they're checked next, in registration order. The auto
router is the least explicit — reflection-based, no manual registration
at all — so it's the last resort, only used when nothing more specific
was found. This ordering means you can always override auto-router
behavior for a specific path just by adding an explicit fixed route.
