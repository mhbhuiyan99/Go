# Go `net/http` Client, Transport & Connection Pooling

Reference notes on Go's standard library HTTP client (`net/http.Client` /
`http.Transport`) — the layer underneath `httplib` (covered in the
External API note), for cases where you need lower-level control:
connection pooling, keep-alive tuning, custom dialers, and mutual TLS.

> **Scope note:** the "External API + timeout/error handling" note covers
> `httplib` (Beego's chainable HTTP client) plus resilience patterns
> (retries, backoff, circuit breakers, idempotency). This note is about
> what's *underneath* — `net/http.Client`/`Transport` — and when to reach
> for it directly instead of `httplib`. `httplib` itself is built on this
> same `Transport` layer, so tuning it also improves `httplib`'s behavior
> if you pass in a custom `http.Client`.

---

# Part 1 — Beginner

## 1. Client vs Transport — two different layers

Go's `net/http` package is split into two main layers: the Client (`http.Client`), a high-level interface that handles cookies, redirects, and timeouts; and the Transport (`http.RoundTripper`), which handles the actual TCP connection, TLS handshakes, and connection pooling.

```go
client := &http.Client{
    Timeout: 10 * time.Second,
}
resp, err := client.Get("https://api.example.com/users")
```

If you don't set `Transport`, the client uses `http.DefaultTransport` — a
shared, package-level `*http.Transport` with generic default settings.
Using `http.DefaultClient` means you're sharing a global transport configuration generally optimized for general-purpose use, not high-throughput backend-to-backend communication.

---

## 2. Basic usage

```go
req, err := http.NewRequest("POST", "https://api.example.com/orders", bytes.NewReader(body))
if err != nil {
    return err
}
req.Header.Set("Content-Type", "application/json")

resp, err := client.Do(req)
if err != nil {
    return err // network-level failure only — see the External API note §5
}
defer resp.Body.Close()

data, err := io.ReadAll(resp.Body)
```

Always `defer resp.Body.Close()` — forgetting this is the most common
resource leak in Go HTTP client code (see §9).

---

## 3. `http.Client.Timeout` vs per-request context

```go
client := &http.Client{Timeout: 10 * time.Second} // whole request/response cycle
```

It's recommended that a REST API client timeout not exceed around 10 seconds — if the requested resource doesn't respond in that time, the connection is canceled with a "Client.Timeout exceeded" error. `Client.Timeout` covers the *entire* round trip: connect, write request, read response headers, read response body. For more granular control (e.g. different limits for connect vs read), use `context.WithTimeout` on the request instead (§8), or `Transport`-level fields like `ResponseHeaderTimeout` (§6).

---

## 4. Why connection pooling exists

If a connection is available in the pool, it's reused (Keep-Alive); if not, a new TCP handshake is required, which is expensive. By default the Go HTTP client performs connection pooling — when a request completes, that connection remains open until the idle connection timeout (default 90 seconds), and if another request comes in, it reuses that established connection instead of creating a new one.

This matters because TCP handshake + TLS handshake (for HTTPS) is real
latency — reusing an existing connection skips both, so pooling directly
improves both latency and CPU/socket overhead for repeated calls to the
same host.

---

## 5. The default `MaxIdleConnsPerHost` gotcha

This is the single most important thing to know before deploying a Go
service that talks to another service heavily:

The default `http.Transport` has a limit on `MaxIdleConnsPerHost`, which defaults to 2. This means if your microservice needs to talk to Service B and you have 100 concurrent requests, Go will create 100 TCP connections, try to put them back in the pool, but keep only 2 of them idle.

**Practical consequence:** under concurrent load against one host, you get
constant connection churn — most connections are opened, used once, and
torn down rather than reused, because the idle pool for that host is
tiny. This silently defeats the entire point of connection pooling and
adds handshake latency to almost every request.

```go
t := http.DefaultTransport.(*http.Transport).Clone()
t.MaxIdleConns = 100        // total idle connections, all hosts combined
t.MaxIdleConnsPerHost = 100 // idle connections kept open, per host
t.MaxConnsPerHost = 100     // hard cap on total (idle + active) per host

client := &http.Client{
    Timeout:   10 * time.Second,
    Transport: t,
}
```

Increasing connections per host and total idle connections increases performance and serves more requests with minimal server resources.

---

## 6. Full custom Transport — the fields that matter

```go
transport := &http.Transport{
    MaxIdleConns:        100,
    MaxIdleConnsPerHost:  20,
    MaxConnsPerHost:     100,
    IdleConnTimeout:      90 * time.Second,

    DialContext: (&net.Dialer{
        Timeout:   5 * time.Second,  // time to establish the TCP connection
        KeepAlive: 30 * time.Second, // TCP-level keepalive probe interval
    }).DialContext,

    TLSHandshakeTimeout:   5 * time.Second,
    ResponseHeaderTimeout: 5 * time.Second, // time to wait for response headers
    ExpectContinueTimeout: 1 * time.Second,

    ForceAttemptHTTP2: true, // attempt HTTP/2 even with a custom DialContext
}
```

These fields give fine-grained control: `MaxIdleConns` caps idle connections across all hosts, `MaxIdleConnsPerHost` caps idle connections per host, `MaxConnsPerHost` caps total connections per host (0 = unlimited), `IdleConnTimeout` controls how long idle connections stay pooled, `DialContext` sets TCP connection/keepalive timing, `TLSHandshakeTimeout` bounds the TLS handshake, `ResponseHeaderTimeout` bounds waiting for response headers, and `ExpectContinueTimeout` bounds waiting for a 100-continue response.

# Part 2 — Advanced

## 8. Context-based timeouts vs `Client.Timeout`

`Client.Timeout` is a blunt, whole-client setting. For per-request control
(especially propagating a deadline from an incoming request, as in the
External API note §10):

```go
ctx, cancel := context.WithTimeout(parentCtx, 3*time.Second)
defer cancel()

req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := client.Do(req)
```

If the context is cancelled or its deadline passes, `client.Do` returns
promptly with an error — this composes with `Client.Timeout` (whichever
fires first wins) and is the mechanism that lets an incoming request's
cancellation propagate into outgoing calls.

---

## 9. Response body leaks — the classic goroutine/socket leak

```go
resp, err := client.Do(req)
if err != nil {
    return err
}
// BUG: no defer resp.Body.Close() — connection can never be returned to the pool
data, _ := io.ReadAll(resp.Body)
```

**Two separate mistakes, both common:**
1. Not calling `resp.Body.Close()` at all — the underlying connection can
   never be reused or released, leaking file descriptors over time.
2. Closing the body but not fully reading it first — Go can only return a
   connection to the idle pool for reuse if the body was drained to EOF;
   closing early on a partially-read body causes the connection to be
   discarded instead of pooled, silently degrading your pooling benefits
   even though nothing "leaks" per se.

```go
resp, err := client.Do(req)
if err != nil {
    return err
}
defer resp.Body.Close()
data, err := io.ReadAll(resp.Body) // drain fully before Close for reuse
```

---

## 10. Sizing the pool for your actual traffic pattern

With the default idle pool (2 per host), a load test produced a peak of over 22,000 goroutines under load; with `MaxIdleConnsPerHost` raised to 100, the same load produced a peak of only 482 goroutines for the same traffic — a direct, measured illustration of how badly the default starves high-concurrency single-host traffic.

**Sizing guidance:**
- `MaxIdleConnsPerHost` — set close to your expected steady-state
  concurrency against that host, not just "a bigger number." Too small:
  constant reconnects. Too large: you hold open more idle sockets than
  you'll ever reuse, wasting both your own file descriptors and the
  remote server's connection slots.
- `MaxConnsPerHost` — a hard ceiling (idle + active). Useful as a
  backpressure mechanism — if you cap this below what a traffic spike
  would otherwise generate, Go queues excess requests waiting for a
  connection to free up rather than opening unbounded new ones, which
  protects both your own service and the downstream one from being
  overwhelmed.
- If you talk to **many different hosts** (fan-out to many microservices),
  `MaxIdleConns` (total, all hosts) matters more than any single host's
  `MaxIdleConnsPerHost`.

## 11. Mutual TLS (mTLS) and custom certificates

```go
cert, err := tls.LoadX509KeyPair("client.crt", "client.key")
if err != nil {
    // handle
}

caCert, _ := os.ReadFile("ca.crt")
caPool := x509.NewCertPool()
caPool.AppendCertsFromPEM(caCert)

transport := &http.Transport{
    TLSClientConfig: &tls.Config{
        Certificates: []tls.Certificate{cert}, // client cert for mTLS
        RootCAs:      caPool,                  // custom CA to trust
    },
}
client := &http.Client{Transport: transport}
```

Used when calling an internal service that requires client-certificate
authentication (common in service-mesh/zero-trust internal networks), or
when the server's certificate is signed by an internal/private CA that
isn't in the OS trust store.

## 12. `RoundTripper` — wrapping the transport for cross-cutting concerns

`http.RoundTripper` is the interface `Transport` implements. Wrapping it
is the raw-`net/http` equivalent of `httplib`'s filter chain (External API
note §12) — useful when you're not using `httplib` at all:

```go
type loggingRoundTripper struct {
    next http.RoundTripper
}

func (l *loggingRoundTripper) RoundTrip(req *http.Request) (*http.Response, error) {
    start := time.Now()
    resp, err := l.next.RoundTrip(req)
    log.Printf("%s %s took %s", req.Method, req.URL, time.Since(start))
    return resp, err
}

client := &http.Client{
    Transport: &loggingRoundTripper{next: http.DefaultTransport},
}
```

This same pattern is how most Go tracing/metrics libraries (OpenTelemetry
instrumentation, etc.) hook into outgoing HTTP calls — they wrap your
`Transport` rather than requiring you to change every call site.

---

## 13. HTTP/2 and its effect on connection pooling assumptions

`ForceAttemptHTTP2: true` makes Go attempt HTTP/2 even with a custom `DialContext`. This matters for pooling because HTTP/2 **multiplexes many requests over a single TCP connection**, unlike HTTP/1.1 where each in-flight request typically needs its own connection. If the host you're calling supports HTTP/2, your effective concurrency per connection is much higher, and `MaxIdleConnsPerHost` tuning matters less than it does for HTTP/1.1-only hosts — worth checking which protocol you're actually negotiating (`resp.Proto`) before assuming your pool-sizing math is correct.

---

## 14. When to use raw `net/http` instead of `httplib`

- You need **fine-grained Transport control** (custom dialers, mTLS,
  HTTP/2 forcing, precise per-phase timeouts) beyond what `httplib`
  exposes.
- You're writing a **shared internal client library** used across many
  services, where you want a single well-tuned `http.Client`/`Transport`
  instance reused everywhere (see §15) rather than `httplib`'s per-request
  builder style.
- You need to integrate with **third-party Go libraries that expect a
  `*http.Client`** directly (very common — e.g. cloud SDKs, gRPC-gateway
  clients) rather than a Beego-specific type.
- Otherwise, `httplib`'s chainable builder and built-in retry/filter-chain
  support (External API note) is usually less boilerplate for typical
  application-level external API calls.

---

## 15. Reuse the client — don't construct one per request

```go
// BAD — a new Transport (and connection pool) is created every call,
// meaning pooling never actually kicks in.
func fetchUser(id string) (*User, error) {
    client := &http.Client{Timeout: 5 * time.Second}
    // ...
}

// GOOD — one client, constructed once, reused across all calls.
var httpClient = &http.Client{
    Timeout:   5 * time.Second,
    Transport: tunedTransport,
}

func fetchUser(id string) (*User, error) {
    resp, err := httpClient.Get("https://api.example.com/users/" + id)
    // ...
}
```

This is the single most common way connection pooling silently doesn't
work in real codebases — a fresh `Transport` (via a fresh `http.Client`)
has an empty idle pool every time, so every request effectively pays full
handshake cost regardless of how well-tuned the `Transport` struct looks
on paper.

# Part 3 — Use-Case Q&A

**Q: Your service makes heavy concurrent calls to one downstream host and profiling shows constant new TCP connections instead of reuse. What's the most likely cause?**

The default `MaxIdleConnsPerHost` is 2 — under real concurrency (say, 100
concurrent requests to one host), Go opens all the connections it needs
but only keeps 2 idle afterward, so almost every subsequent request pays
a full TCP+TLS handshake instead of reusing a pooled connection. Clone
`http.DefaultTransport`, raise `MaxIdleConnsPerHost` (and `MaxIdleConns`)
to match your actual concurrency, and set that `Transport` on a
long-lived, reused `http.Client`.

---

**Q: You tuned `MaxIdleConnsPerHost` to 100 but you're still seeing constant reconnects. What else could be wrong?**

You're likely constructing a new `http.Client` (and therefore a new
`Transport` with an empty pool) on every function call instead of reusing
one long-lived client. A perfectly-tuned `Transport` struct does nothing
if a fresh instance is created per request — the idle pool has to persist
across requests to actually help.

---

**Q: When would `Client.Timeout` alone not be enough, and you'd reach for `context.WithTimeout` instead?**

When you need the timeout to originate from an *upstream* deadline (e.g.
the incoming request's own remaining time budget) rather than a fixed
value baked into the client, or when you need different requests on the
same shared client to have different timeouts. `Client.Timeout` is
per-client and static; `context.WithTimeout` on individual requests is
per-call and dynamic, and it's also what lets cancellation propagate from
an incoming request into an outgoing one.

---

**Q: A teammate's code does `resp, _ := client.Do(req)` then `resp.Body.Close()` without reading the body first. What's wrong, even though nothing crashes?**

Go can only return a connection to the idle pool for reuse if the
response body was fully read to EOF before closing. Closing early (without
draining the body) means the connection gets discarded instead of pooled
— it's not a crash or a leak exactly, but it silently defeats connection
reuse, which is the same practical problem as the `MaxIdleConnsPerHost`
issue above, just caused by application code instead of Transport config.

---

**Q: You're building a shared internal Go library that multiple services will use to call a common downstream API. Why does it matter that the `http.Client` be constructed once at package/library init, not per call?**

Because the connection pool lives on the `Transport` inside the
`http.Client` — constructing a new client per call means every call
starts with a cold, empty pool, guaranteeing a fresh handshake every time
regardless of how the `Transport` fields are tuned. A shared library
should own and expose one well-configured, long-lived client (or accept
an injected one) that all its calls funnel through.

---

**Q: How would you add request logging/tracing to every outgoing call made through a raw `http.Client`, without editing every call site?**

Wrap `http.RoundTripper` — implement a type that embeds/calls the real
transport and adds logic before/after calling `next.RoundTrip(req)`, then
set it as the client's `Transport`. This is the same "wrap around the
pipeline" idea as `httplib`'s filter chain or a server-side `FilterChain`
(see the Filters & Middleware note) — cross-cutting concerns belong in one
wrapping layer, not scattered across every call site.

---

**Q: You're calling a host that supports HTTP/2. Does `MaxIdleConnsPerHost` tuning still matter as much?**

Less than for HTTP/1.1. HTTP/2 multiplexes many concurrent requests over
a single TCP connection, so you don't need nearly as many separate pooled
connections per host to get good concurrency — the pooling math that
matters for HTTP/1.1 (roughly one connection per concurrent in-flight
request) doesn't directly apply. Worth confirming via `resp.Proto` which
protocol is actually in use before tuning pool size numbers that assume
HTTP/1.1 behavior.

---

**Q: Why might you choose raw `net/http.Client` over `httplib` for a specific integration, even though `httplib` is more convenient day-to-day?**

Typically because a third-party SDK or library expects a `*http.Client`
directly (very common with cloud provider SDKs), or because you need
Transport-level control — mTLS, custom dialers, forced HTTP/2, precise
per-phase timeouts — that goes beyond what `httplib`'s builder API
exposes. For ordinary application-level calls to your own or a partner's
REST API, `httplib`'s built-in retries and filter chain usually mean less
boilerplate.
