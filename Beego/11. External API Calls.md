# External API Calls, Timeouts & Error Handling

Reference notes on calling external/third-party APIs from a Beego app using
`github.com/beego/beego/v2/client/httplib`, plus the broader patterns for
timeouts, retries, and error handling that apply whenever your service
depends on another service over the network.

---

# Part 1 — Beginner

## 1. Why this is a distinct topic from routing/controllers

Everything covered so far (`04. Routing.md`, `05. Controllers.md`, cache,
ORM) is about your app serving *incoming* requests. This note is about the
opposite direction: your app making *outgoing* calls to other APIs — and
critically, what happens when that other service is slow, down, or
returns something unexpected. This is where a huge share of real
production incidents come from, so it gets its own use-case-heavy
treatment.

---

## 2. `httplib` — Beego's HTTP client

```bash
go get github.com/beego/beego/v2/client/httplib
```

```go
import "github.com/beego/beego/v2/client/httplib"

req := httplib.Get("https://api.example.com/users/1")
str, err := req.String()
if err != nil {
    // network error, timeout, non-2xx handling, etc.
}
fmt.Println(str)
```

httplib supports Get, Post, Put, Delete, and Head as the basic request methods. It's a thin, chainable wrapper around Go's standard `net/http` client — you're not learning a separate HTTP stack, just a more convenient builder API.

---

## 3. Building a request

```go
req := httplib.Post("https://api.example.com/orders")
req.Param("customer_id", "123")     // form param
req.Header("Authorization", "Bearer "+token)
req.JSONBody(map[string]interface{}{ // JSON body (alternative to Param)
    "customer_id": 123,
    "amount":      49.99,
})

var result OrderResponse
err := req.ToJSON(&result) // send + decode JSON response directly into a struct
```

Common terminal methods: `.String()` (raw body as string), `.ToJSON(&v)`,
`.ToXML(&v)`, `.ToFile(path)`, `.Bytes()`, `.Response()` (raw `*http.Response`
for full control).

---

## 4. Setting timeouts

The default timeout is 60 seconds; set it with `SetTimeout(connectTimeout, readWriteTimeout time.Duration)`.

```go
str, err := httplib.Get("https://api.example.com/slow").
    SetTimeout(5*time.Second, 10*time.Second).
    String()
```

- **connectTimeout** — how long to wait for the TCP connection (and TLS
  handshake) to establish.
- **readWriteTimeout** — how long to wait for data once connected (covers
  sending the request body and reading the response).

**Never rely on the 60-second default for a request inside a user-facing
API path** — if the downstream service hangs, your own endpoint hangs for
a full minute, and that latency propagates to whoever called *you*. Set an
explicit, deliberately short timeout appropriate to the call.

---

## 5. Basic error handling

```go
resp, err := httplib.Get(url).SetTimeout(3*time.Second, 5*time.Second).Response()
if err != nil {
    // network-level failure: DNS, connection refused, timeout, TLS error
    return fmt.Errorf("calling external API: %w", err)
}
defer resp.Body.Close()

if resp.StatusCode >= 500 {
    // downstream server error — often transient, may be worth retrying
} else if resp.StatusCode >= 400 {
    // client-side error — your request was malformed; retrying won't help
} else if resp.StatusCode >= 200 && resp.StatusCode < 300 {
    // success — parse the body
}
```

The critical beginner mistake: `err` from `httplib`/`net/http` is **only
non-nil for network-level failures** (couldn't connect, timed out, TLS
error). A `404` or `500` response is still a "successful" HTTP round trip
as far as `err` is concerned — you must check `resp.StatusCode` yourself.

## 6. TLS and auth basics

```go
req.SetTLSClientConfig(&tls.Config{InsecureSkipVerify: true}) // dev/testing only
req.SetBasicAuth("user", "passwd")
req.Header("Authorization", "Bearer "+token)
```

> ⚠️ `InsecureSkipVerify: true` disables certificate validation — fine for
> local testing against a self-signed cert, never acceptable in production
> since it makes you vulnerable to man-in-the-middle attacks.

# Part 2 — Advanced

## 8. Built-in retries

```go
req := httplib.Get("https://api.example.com/data").
    Retries(3).            // retry up to 3 times on failure (-1 = retry forever)
    RetryDelay(500 * time.Millisecond)
```

`Retries(times int)` sets the number of retries — default is 0 (no retry); -1 means retry forever; any other value is a fixed retry count.

**What actually gets retried:** network-level failures (connection errors,
timeouts). By default this does **not** distinguish "worth retrying" (5xx,
network blip) from "never retry" (4xx) — you generally want to check the
status code yourself and only retry on 5xx/network errors, not blindly
retry a 400 that will just fail identically every time.

> ⚠️ `Retries(-1)` (retry forever) inside a request-handling path is a real
> footgun — a permanently-down downstream service will hang your handler
> indefinitely (or until your own outer timeout/context cancels it). Only
> use unbounded retries for background jobs with their own cancellation
> logic, never inline in a request handler.

---

## 9. Exponential backoff and jitter

Fixed-delay retries (`RetryDelay(500ms)` every time) can synchronize
retries across many clients into repeated bursts against an already
struggling service — the same "thundering herd" problem covered in the
cache note. Prefer exponential backoff with jitter for anything beyond a
couple of quick retries:

```go
func callWithBackoff(url string, maxAttempts int) (string, error) {
    var lastErr error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        str, err := httplib.Get(url).SetTimeout(2*time.Second, 3*time.Second).String()
        if err == nil {
            return str, nil
        }
        lastErr = err
        backoff := time.Duration(1<<attempt) * 100 * time.Millisecond
        jitter := time.Duration(rand.Intn(100)) * time.Millisecond
        time.Sleep(backoff + jitter)
    }
    return "", fmt.Errorf("all %d attempts failed: %w", maxAttempts, lastErr)
}
```

## 10. Context-based cancellation and deadlines

`httplib`'s `SetTimeout` bounds a single request. For propagating a
deadline from the *incoming* request into the outgoing call (so a client
who gives up waiting doesn't leave your server still working on a
now-pointless downstream call):

```go
func (c *OrderController) Get() {
    ctx, cancel := context.WithTimeout(c.Ctx.Request.Context(), 3*time.Second)
    defer cancel()

    req := httplib.Get("https://api.example.com/inventory").WithContext(ctx)
    // ...
}
```

Using `c.Ctx.Request.Context()` as the parent means if the original caller
disconnects, the outgoing call is cancelled too — avoiding wasted work on
a response nobody's waiting for anymore.

## 11. Circuit breakers

Retries handle transient blips; a **circuit breaker** handles sustained
downstream outages — instead of every request hammering (and waiting on
the timeout of) a service that's clearly down, the breaker "trips" after
enough consecutive failures and starts failing fast immediately, without
even attempting the call, for a cooldown period.

```go
type CircuitBreaker struct {
    mu           sync.Mutex
    failures     int
    threshold    int
    open         bool
    openedAt     time.Time
    cooldown     time.Duration
}

func (cb *CircuitBreaker) Call(fn func() error) error {
    cb.mu.Lock()
    if cb.open {
        if time.Since(cb.openedAt) < cb.cooldown {
            cb.mu.Unlock()
            return errors.New("circuit open: downstream unavailable")
        }
        cb.open = false // cooldown elapsed, allow a trial request through
    }
    cb.mu.Unlock()

    err := fn()

    cb.mu.Lock()
    defer cb.mu.Unlock()
    if err != nil {
        cb.failures++
        if cb.failures >= cb.threshold {
            cb.open = true
            cb.openedAt = time.Now()
        }
        return err
    }
    cb.failures = 0
    return nil
}
```

**Why this matters beyond "nice to have":** without a breaker, a downstream
outage means every request to your service still waits out the full
timeout on every call, multiplying the outage's impact on your own
latency and potentially exhausting your own connection pool / goroutines.
Failing fast during a known outage protects your service's own health.

For production use, prefer a maintained library (e.g. `sony/gobreaker`)
over a hand-rolled one — the concurrency edge cases (half-open state,
concurrent trial requests) are easy to get subtly wrong.

## 12. Using httplib's filter chain for cross-cutting concerns (AOP)

httplib has a filter-chain design (similar in spirit to the server-side filters) for AOP-style concerns like logging and tracing on outgoing requests.

```go
loggingFilter := func(next httplib.Filter) httplib.Filter {
    return func(ctx context.Context, req *httplib.BeegoHTTPRequest) (*http.Response, error) {
        start := time.Now()
        resp, err := next(ctx, req)
        log.Printf("outgoing call took %s, err=%v", time.Since(start), err)
        return resp, err
    }
}

req := httplib.Get(url).AddFilters(loggingFilter)
```

Use this the same way you'd use a server-side `FilterChain` (see the
Filters & Middleware note) — for logging every outgoing call, injecting
trace headers for distributed tracing, or centralizing metrics collection
on external API calls, without repeating that boilerplate at every call
site.

## 13. Idempotency and retry safety

Retrying a `GET` is always safe (it shouldn't have side effects). Retrying
a `POST` (e.g. "create an order") is **not** automatically safe — if the
first attempt actually succeeded but the response was lost (timeout on
the way back), a naive retry can create a duplicate order.

**Mitigation: idempotency keys.**

```go
req := httplib.Post("https://api.example.com/orders").
    Header("Idempotency-Key", orderRequestUUID)
```

Many payment/commerce APIs (Stripe being the canonical example) support an
idempotency key header — the server recognizes a retried request with the
same key and returns the original result instead of creating a duplicate.
If the external API you're calling doesn't support this, only retry
non-mutating calls automatically, and handle POST/PUT/DELETE retries more
carefully (e.g. check-before-retry, or make the mutation itself naturally
idempotent — like "set status to X" rather than "increment counter").

## 14. Distinguishing error types for actual handling logic

A mature error-handling layer classifies failures instead of treating
"anything went wrong" as one bucket:

| Failure type | Example | Retry? | User-facing response |
|---|---|---|---|
| Network timeout/connection refused | Downstream host unreachable | Yes, with backoff | 503/504 to your own caller |
| DNS failure | Bad hostname config | No — config bug | 500, alert |
| 4xx from downstream | Your request was malformed | No | Fix the request, don't retry blindly |
| 5xx from downstream | Downstream's own bug/overload | Yes, with backoff | 503/504 to your own caller |
| 429 from downstream | Downstream rate-limited you | Yes, honoring `Retry-After` header | Back off, don't hammer |
| Malformed/unexpected response body | Downstream API changed shape | No — needs a code fix | 502, alert |

```go
resp, err := httplib.Get(url).SetTimeout(3*time.Second, 5*time.Second).Response()
if err != nil {
    return ErrDownstreamUnavailable // network-level — safe to retry
}
switch {
case resp.StatusCode == 429:
    retryAfter := resp.Header.Get("Retry-After")
    // honor it rather than retrying immediately
case resp.StatusCode >= 500:
    return ErrDownstreamServerError // safe to retry
case resp.StatusCode >= 400:
    return ErrDownstreamRejectedRequest // don't retry, it'll fail the same way
}
```

## 15. Combining with the cache module (avoid redundant external calls)

If the external API is slow, rate-limited, or costs money per call,
combine timeout/retry handling with the cache module (see the cache note):

```go
func getExchangeRate(ctx context.Context, bm cache.Cache) (float64, error) {
    if v, err := bm.Get(ctx, "rate:usd_eur"); err == nil && v != nil {
        return v.(float64), nil
    }
    rate, err := fetchRateFromExternalAPI()
    if err != nil {
        return 0, err
    }
    _ = bm.Put(ctx, "rate:usd_eur", rate, 5*time.Minute)
    return rate, nil
}
```

This is the same cache-aside pattern from the cache note, just with an
external API instead of a DB as the source of truth — and it directly
reduces how often you're exposed to that API's own latency/failure modes.

## 16. Testing external API calls

Never hit the real external API in unit tests — it's slow, flaky, and
possibly rate-limited or costly. Use `httptest.NewServer` to stand up a
local fake:

```go
func TestFetchUser(t *testing.T) {
    ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(200)
        w.Write([]byte(`{"id": 1, "name": "Test User"}`))
    }))
    defer ts.Close()

    user, err := fetchUser(ts.URL) // your function, pointed at the fake server
    if err != nil {
        t.Fatal(err)
    }
    if user.Name != "Test User" {
        t.Errorf("got %s", user.Name)
    }
}
```

For timeout/error-path tests specifically, make the fake server sleep past
your configured timeout, or return specific status codes/malformed bodies,
to verify your handling logic actually does the right thing under those
conditions rather than only testing the happy path.

# Part 3 — Use-Case Q&A

**Q: Your endpoint calls a third-party API with the default `httplib` settings, and under load your whole service starts timing out. Why?**

The default 60-second timeout means every request to your endpoint is
held open for up to a full minute if the downstream service is slow —
under concurrent load, that ties up goroutines/connections for a long
time each, and your own server can run out of capacity waiting on a
service you don't control. Set an explicit, short timeout appropriate to
what the caller can tolerate, and consider a circuit breaker so a
sustained outage fails fast instead of everyone waiting out the timeout.

---

**Q: You added `Retries(3)` to a `POST /orders` call. What's the actual risk here?**

If the first `POST` succeeded on the server side but the response was
lost (e.g. a timeout on the way back), the retry sends a second, distinct
`POST` — potentially creating a duplicate order. Retries are safe by
default for `GET` (no side effects) but not for `POST`/`PUT`/`DELETE`
unless the API supports idempotency keys or the operation is naturally
idempotent. Blindly retrying mutating calls is a common source of
duplicate-charge/duplicate-record bugs.

---

**Q: `err` was `nil` from your `httplib` call, but your code still crashed trying to parse the response as valid data. What went wrong?**

`err` from the HTTP client only reflects network-level failure — a `404`
or `500` response is still a "successful" round trip as far as `err` is
concerned. You have to check `resp.StatusCode` yourself before assuming
the body is the shape you expect; skipping that check is the single most
common mistake in beginner external-API integration code.

---

**Q: A downstream service starts returning `429 Too Many Requests`. What's the correct response, versus what a naive retry loop does wrong?**

Correct: read the `Retry-After` header (if present) and back off for that
duration before trying again — you're being told exactly how long to
wait. A naive retry loop that immediately retries on any non-2xx makes the
rate-limiting worse, potentially getting your client blocked entirely.
429 needs different handling than a generic 5xx retry.

---

**Q: Why prefer exponential backoff with jitter over a fixed retry delay when calling a struggling downstream API?**

A fixed delay (e.g. every client retries exactly 500ms later) synchronizes
retries from many concurrent callers into repeated bursts hitting the
already-struggling service at the same moments — the same thundering-herd
problem covered in the cache note. Exponential backoff spreads retries
out over increasing intervals, and jitter desynchronizes different
clients' retry timing so they don't all pile on at once.

---

**Q: When would you add a circuit breaker on top of retries, instead of just retrying more aggressively?**

When the downstream outage is sustained, not transient — retries (even
with backoff) still mean every request pays the cost of attempting and
timing out against a service that's clearly down. A circuit breaker trips
after enough consecutive failures and starts failing fast (no network
call at all) for a cooldown window, protecting your own service's latency
and resource usage during someone else's outage, then automatically tests
recovery afterward.

---

**Q: How do you unit-test what your code does when an external API times out, without actually waiting for a real timeout in your test suite?**

Point your code at a local `httptest.NewServer` whose handler deliberately
sleeps longer than your configured timeout (using a short timeout in the
test, e.g. 50ms, not your real production value), and assert your code's
error-handling path behaves correctly — without needing a real flaky
external dependency or a slow test run.

---

**Q: You're calling an external exchange-rate API on every request to convert prices, and it's both slow and rate-limited. What's the fix?**

Cache the result (cache-aside pattern) with a TTL appropriate to how often
the rate actually needs to be fresh — e.g. 5 minutes for a currency rate
that doesn't need per-request accuracy. This directly reduces both your
exposure to the API's latency and your risk of hitting its rate limit,
and it's the same pattern as any other expensive-external-call caching
scenario.

---

**Q: A client cancels their request (closes the connection) while your handler is mid-way through calling a slow external API. What happens by default, and how do you fix it?**

By default, nothing stops the outgoing call — your handler keeps waiting
on the external API and doing pointless work for a response nobody will
receive. Propagate the incoming request's context (`c.Ctx.Request.Context()`)
into the outgoing `httplib` call via `WithContext`, so cancellation
upstream cancels the downstream call too, freeing up resources
immediately instead of waiting out the full timeout.
