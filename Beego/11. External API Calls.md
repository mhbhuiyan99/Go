# External API Calls, Timeouts & Error Handling

Reference notes on calling external/third-party APIs from a Go/Beego app —
building requests, timeouts, retries, and error handling patterns that
apply whenever your service depends on another service over the network.

> **Scope note:** this note focuses on *resilience patterns* — timeouts,
> retries, backoff, circuit breakers, idempotency, error classification.
> For deep `Transport`-level tuning (connection pooling, `MaxIdleConnsPerHost`,
> mTLS, `RoundTripper` wrapping), see the separate Go `net/http` Client,
> Transport & Connection Pooling note — everything here builds on top of
> that layer.

---

# Part 1 — Beginner

## 1. Why this is a distinct topic from routing/controllers

Everything covered elsewhere (routing, controllers, cache, ORM) is about
your app serving *incoming* requests. This note is about the opposite
direction: your app making *outgoing* calls to other APIs — and critically,
what happens when that other service is slow, down, or returns something
unexpected. This is where a large share of real production incidents come
from, so it gets its own use-case-heavy treatment.

---

## 2. Choosing an HTTP client: `net/http.Client` vs `httplib`

Two options exist for making outgoing calls from a Beego app:

| | `net/http.Client` (standard library) | `httplib` (`github.com/beego/beego/v2/client/httplib`) |
|---|---|---|
| **Portability** | Works everywhere, framework-agnostic | Beego-specific |
| **Third-party integration** | Nearly all Go SDKs/libraries (cloud providers, tracing tools, gRPC-gateway clients) expect a `*http.Client` directly | Many libraries won't accept it |
| **Transport-level control** | Full control — pooling, mTLS, custom dialers, `RoundTripper` wrapping | Wraps `Transport` but exposes less directly |
| **Ecosystem** | The one every Go developer already knows | Smaller, Beego-only audience |
| **Convenience for quick calls** | A bit more boilerplate | Chainable builder, built-in retries |

**Recommendation used throughout this note: `net/http.Client`.** It's
framework-agnostic, it's what most teams (and most instructors) actually
use in production Go code, and it's what you'll need anyway the moment you
pass a client into a third-party SDK. `httplib` is documented separately
in §7 as a valid, more convenient alternative for quick internal calls
within a Beego-only codebase — but default to `net/http.Client` unless you
have a specific reason not to.

---

## 3. Basic client setup and a request

```go
var httpClient = &http.Client{
    Timeout: 10 * time.Second, // whole request/response cycle — see §5
}

func fetchUser(ctx context.Context, id string) (*User, error) {
    req, err := http.NewRequestWithContext(ctx, "GET",
        "https://api.example.com/users/"+id, nil)
    if err != nil {
        return nil, err
    }

    resp, err := httpClient.Do(req)
    if err != nil {
        return nil, err // network-level failure — see §6
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf("unexpected status: %d", resp.StatusCode)
    }

    var user User
    if err := json.NewDecoder(resp.Body).Decode(&user); err != nil {
        return nil, err
    }
    return &user, nil
}
```

**Construct the client once, reuse it everywhere** — a package-level
`var httpClient = &http.Client{...}`, not a new one per function call. A
fresh `http.Client` means a fresh, empty connection pool every time,
which defeats connection reuse entirely (see the HTTP Client/Transport
note for why this matters).

---

## 4. Building requests: headers, JSON bodies, query params

```go
body, _ := json.Marshal(map[string]interface{}{
    "customer_id": 123,
    "amount":      49.99,
})

req, _ := http.NewRequestWithContext(ctx, "POST",
    "https://api.example.com/orders", bytes.NewReader(body))
req.Header.Set("Content-Type", "application/json")
req.Header.Set("Authorization", "Bearer "+token)

resp, err := httpClient.Do(req)
```

For query parameters, build via `url.Values` rather than string
concatenation, which handles escaping correctly:

```go
u, _ := url.Parse("https://api.example.com/search")
q := u.Query()
q.Set("term", searchTerm)
u.RawQuery = q.Encode()

req, _ := http.NewRequestWithContext(ctx, "GET", u.String(), nil)
```

## 5. Setting timeouts

```go
httpClient := &http.Client{Timeout: 10 * time.Second}
```

`Client.Timeout` covers the *entire* round trip: connect, write request,
read response headers, read response body. A REST API client timeout
generally shouldn't exceed around 10 seconds for a user-facing call — if
the resource doesn't respond in time, the request is canceled with a
"Client.Timeout exceeded" error.

**Never rely on an unbounded/default timeout for a request inside a
user-facing API path** — if the downstream service hangs, your own
endpoint hangs too, and that latency propagates to whoever called *you*.
For per-request (rather than whole-client) timeout control, see
`context.WithTimeout` in §10.

## 6. Basic error handling

```go
resp, err := httpClient.Do(req)
if err != nil {
    // network-level failure: DNS, connection refused, timeout, TLS error
    return fmt.Errorf("calling external API: %w", err)
}
defer resp.Body.Close()

switch {
case resp.StatusCode >= 500:
    // downstream server error — often transient, may be worth retrying
case resp.StatusCode >= 400:
    // client-side error — your request was malformed; retrying won't help
case resp.StatusCode >= 200 && resp.StatusCode < 300:
    // success — parse the body
}
```

The critical beginner mistake: `err` from `net/http` is **only non-nil for
network-level failures** (couldn't connect, timed out, TLS error). A `404`
or `500` response is still a "successful" HTTP round trip as far as `err`
is concerned — you must check `resp.StatusCode` yourself.

---

## 7. `httplib` as an alternative

For quick, internal, Beego-only calls where the convenience is worth the
framework coupling, `httplib` offers a chainable builder:

```go
import "github.com/beego/beego/v2/client/httplib"

req := httplib.Get("https://api.example.com/users/1").
    SetTimeout(5*time.Second, 10*time.Second)

var user User
err := req.ToJSON(&user) // send + decode in one call
```

It supports `Get`/`Post`/`Put`/`Delete`/`Head`, `.Param()`/`.JSONBody()`
for the request body, `.ToJSON()`/`.ToXML()`/`.String()` for the response,
and built-in `.Retries(n)`. Everything from §8 onward (retries, backoff,
circuit breakers, idempotency) applies conceptually to `httplib` too — the
patterns are the same, just wire them around `httplib`'s builder instead
of `http.Client.Do()` if you choose this path. See its own reference
(if you're keeping a dedicated section for it) for the full method list.

# Part 2 — Advanced

## 9. Manual retries

`net/http` has no built-in retry mechanism — you write a small helper:

```go
func doWithRetry(ctx context.Context, req *http.Request, maxAttempts int) (*http.Response, error) {
    var lastErr error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        resp, err := httpClient.Do(req)
        if err == nil && resp.StatusCode < 500 {
            return resp, nil // success or non-retryable client error
        }
        if err == nil {
            resp.Body.Close() // drain/close before retrying — see the Transport note
        }
        lastErr = err
        time.Sleep(time.Duration(attempt+1) * 200 * time.Millisecond)
    }
    return nil, fmt.Errorf("all %d attempts failed: %w", maxAttempts, lastErr)
}
```

**What's actually worth retrying:** network-level failures and 5xx
responses. Never blindly retry a 4xx — it will fail identically every
time, since the problem is your request, not the network or the
downstream service's transient state.

> ⚠️ An unbounded retry loop inside a request-handling path is a real
> footgun — a permanently-down downstream service will hang your handler
> indefinitely (or until an outer context deadline cancels it). Bound
> `maxAttempts`, and prefer unbounded retries only in background jobs with
> their own cancellation logic.

---

## 10. Exponential backoff and jitter

Fixed-delay retries can synchronize retries across many clients into
repeated bursts against an already struggling service — the same
"thundering herd" problem covered in the cache note. Prefer exponential
backoff with jitter for anything beyond a couple of quick retries:

```go
func callWithBackoff(ctx context.Context, url string, maxAttempts int) (string, error) {
    var lastErr error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
        resp, err := httpClient.Do(req)
        if err == nil && resp.StatusCode == 200 {
            defer resp.Body.Close()
            data, _ := io.ReadAll(resp.Body)
            return string(data), nil
        }
        if err == nil {
            resp.Body.Close()
        }
        lastErr = err
        backoff := time.Duration(1<<attempt) * 100 * time.Millisecond
        jitter := time.Duration(rand.Intn(100)) * time.Millisecond
        select {
        case <-time.After(backoff + jitter):
        case <-ctx.Done():
            return "", ctx.Err()
        }
    }
    return "", fmt.Errorf("all %d attempts failed: %w", maxAttempts, lastErr)
}
```

Note the `select` on `ctx.Done()` during the sleep — this lets an outer
cancellation (§11) interrupt the retry loop immediately instead of
finishing out the backoff sleep pointlessly.

## 11. Context-based cancellation and deadlines

For propagating a deadline from the *incoming* request into the outgoing
call (so a client who gives up waiting doesn't leave your server still
working on a now-pointless downstream call):

```go
func (c *OrderController) Get() {
    ctx, cancel := context.WithTimeout(c.Ctx.Request.Context(), 3*time.Second)
    defer cancel()

    req, _ := http.NewRequestWithContext(ctx, "GET",
        "https://api.example.com/inventory", nil)
    resp, err := httpClient.Do(req)
    // ...
}
```

Using `c.Ctx.Request.Context()` as the parent means if the original caller
disconnects, the outgoing call is cancelled too — avoiding wasted work on
a response nobody's waiting for anymore. This composes with `Client.Timeout`
— whichever deadline is reached first wins.

## 12. Circuit breakers

Retries handle transient blips; a **circuit breaker** handles sustained
downstream outages — instead of every request hammering (and waiting on
the timeout of) a service that's clearly down, the breaker "trips" after
enough consecutive failures and starts failing fast immediately, without
even attempting the call, for a cooldown period.

```go
type CircuitBreaker struct {
    mu        sync.Mutex
    failures  int
    threshold int
    open      bool
    openedAt  time.Time
    cooldown  time.Duration
}

func (cb *CircuitBreaker) Call(fn func() error) error {
    cb.mu.Lock()
    if cb.open {
        if time.Since(cb.openedAt) < cb.cooldown {
            cb.mu.Unlock()
            return errors.New("circuit open: downstream unavailable")
        }
        cb.open = false // cooldown elapsed, allow a trial request through
    }
    cb.mu.Unlock()

    err := fn()

    cb.mu.Lock()
    defer cb.mu.Unlock()
    if err != nil {
        cb.failures++
        if cb.failures >= cb.threshold {
            cb.open = true
            cb.openedAt = time.Now()
        }
        return err
    }
    cb.failures = 0
    return nil
}
```

Usage — wraps any call, `net/http` or otherwise:

```go
err := breaker.Call(func() error {
    resp, err := httpClient.Do(req)
    if err != nil || resp.StatusCode >= 500 {
        return errors.New("downstream failure")
    }
    resp.Body.Close()
    return nil
})
```

**Why this matters beyond "nice to have":** without a breaker, a downstream
outage means every request still waits out the full timeout on every
call, multiplying the outage's impact on your own latency and potentially
exhausting your own connection pool/goroutines. Failing fast during a
known outage protects your service's own health.

For production use, prefer a maintained library (e.g. `sony/gobreaker`)
over a hand-rolled one — the concurrency edge cases (half-open state,
concurrent trial requests) are easy to get subtly wrong.

## 13. `RoundTripper` wrapping for cross-cutting concerns (AOP)

`net/http`'s equivalent of a filter chain for outgoing calls is wrapping
`http.RoundTripper` — one wrapper covers logging/tracing for every call
made through that client, without repeating boilerplate at each call site:

```go
type loggingRoundTripper struct {
    next http.RoundTripper
}

func (l *loggingRoundTripper) RoundTrip(req *http.Request) (*http.Response, error) {
    start := time.Now()
    resp, err := l.next.RoundTrip(req)
    log.Printf("%s %s took %s", req.Method, req.URL, time.Since(start))
    return resp, err
}

httpClient := &http.Client{
    Transport: &loggingRoundTripper{next: http.DefaultTransport},
}
```

This is the same pattern most Go tracing/metrics libraries (OpenTelemetry
instrumentation, etc.) use to hook into outgoing HTTP calls. Full detail
on `RoundTripper` and `Transport` internals is in the HTTP
Client/Transport note.

## 14. Idempotency and retry safety

Retrying a `GET` is always safe (it shouldn't have side effects). Retrying
a `POST` (e.g. "create an order") is **not** automatically safe — if the
first attempt actually succeeded but the response was lost (timeout on
the way back), a naive retry can create a duplicate order.

**Mitigation: idempotency keys.**

```go
req.Header.Set("Idempotency-Key", orderRequestUUID)
```

Many payment/commerce APIs (Stripe being the canonical example) support an
idempotency key header — the server recognizes a retried request with the
same key and returns the original result instead of creating a duplicate.
If the external API you're calling doesn't support this, only retry
non-mutating calls automatically, and handle POST/PUT/DELETE retries more
carefully (e.g. check-before-retry, or make the mutation itself naturally
idempotent — like "set status to X" rather than "increment counter").

## 15. Distinguishing error types for actual handling logic

A mature error-handling layer classifies failures instead of treating
"anything went wrong" as one bucket:

| Failure type | Example | Retry? | User-facing response |
|---|---|---|---|
| Network timeout/connection refused | Downstream host unreachable | Yes, with backoff | 503/504 to your own caller |
| DNS failure | Bad hostname config | No — config bug | 500, alert |
| 4xx from downstream | Your request was malformed | No | Fix the request, don't retry blindly |
| 5xx from downstream | Downstream's own bug/overload | Yes, with backoff | 503/504 to your own caller |
| 429 from downstream | Downstream rate-limited you | Yes, honoring `Retry-After` header | Back off, don't hammer |
| Malformed/unexpected response body | Downstream API changed shape | No — needs a code fix | 502, alert |

```go
resp, err := httpClient.Do(req)
if err != nil {
    return ErrDownstreamUnavailable // network-level — safe to retry
}
defer resp.Body.Close()

switch {
case resp.StatusCode == 429:
    retryAfter := resp.Header.Get("Retry-After")
    // honor it rather than retrying immediately
case resp.StatusCode >= 500:
    return ErrDownstreamServerError // safe to retry
case resp.StatusCode >= 400:
    return ErrDownstreamRejectedRequest // don't retry, it'll fail the same way
}
```

## 16. Combining with the cache module (avoid redundant external calls)

If the external API is slow, rate-limited, or costs money per call,
combine timeout/retry handling with the cache module (see the cache note):

```go
func getExchangeRate(ctx context.Context, bm cache.Cache) (float64, error) {
    if v, err := bm.Get(ctx, "rate:usd_eur"); err == nil && v != nil {
        return v.(float64), nil
    }
    rate, err := fetchRateFromExternalAPI(ctx)
    if err != nil {
        return 0, err
    }
    _ = bm.Put(ctx, "rate:usd_eur", rate, 5*time.Minute)
    return rate, nil
}
```

This is the same cache-aside pattern from the cache note, just with an
external API instead of a DB as the source of truth — and it directly
reduces how often you're exposed to that API's own latency/failure modes.

## 17. Testing external API calls

Never hit the real external API in unit tests — it's slow, flaky, and
possibly rate-limited or costly. Use `httptest.NewServer` to stand up a
local fake:

```go
func TestFetchUser(t *testing.T) {
    ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(200)
        w.Write([]byte(`{"id": 1, "name": "Test User"}`))
    }))
    defer ts.Close()

    user, err := fetchUser(context.Background(), ts.URL) // pointed at the fake server
    if err != nil {
        t.Fatal(err)
    }
    if user.Name != "Test User" {
        t.Errorf("got %s", user.Name)
    }
}
```

For timeout/error-path tests specifically, make the fake server sleep past
your configured timeout, or return specific status codes/malformed bodies,
to verify your handling logic actually does the right thing under those
conditions rather than only testing the happy path.

# Part 3 — Use-Case Q&A

**Q: Your instructor said to use `net/http.Client` instead of `httplib` — why does that matter in practice?**

Portability and ecosystem fit. `httplib` is Beego-specific — the moment
you need to pass a client into a third-party SDK (cloud provider,
tracing/metrics library, another team's internal Go package), almost all
of them expect a plain `*http.Client`, not a Beego type. `net/http.Client`
code also ports cleanly if logic ever moves out of Beego (a microservice,
a shared library, a CLI tool), and it's the one HTTP client every Go
developer already knows, which matters for code review and onboarding.
`httplib` isn't *wrong*, but `net/http.Client` is the safer default for
anything meant to be reusable or production-facing.

---

**Q: Your endpoint calls a third-party API with an unbounded/default timeout, and under load your whole service starts timing out. Why?**

Without an explicit `Client.Timeout`, a slow downstream service can hold a
request open indefinitely — under concurrent load, that ties up
goroutines/connections for a long time each, and your own server can run
out of capacity waiting on a service you don't control. Set an explicit,
short timeout appropriate to what the caller can tolerate, and consider a
circuit breaker so a sustained outage fails fast instead of everyone
waiting out the timeout.

---

**Q: You added a retry loop to a `POST /orders` call. What's the actual risk here?**

If the first `POST` succeeded on the server side but the response was
lost (e.g. a timeout on the way back), the retry sends a second, distinct
`POST` — potentially creating a duplicate order. Retries are safe by
default for `GET` (no side effects) but not for `POST`/`PUT`/`DELETE`
unless the API supports idempotency keys or the operation is naturally
idempotent. Blindly retrying mutating calls is a common source of
duplicate-charge/duplicate-record bugs.

---

**Q: `err` was `nil` from your `http.Client.Do()` call, but your code still crashed trying to parse the response as valid data. What went wrong?**

`err` from the HTTP client only reflects network-level failure — a `404`
or `500` response is still a "successful" round trip as far as `err` is
concerned. You have to check `resp.StatusCode` yourself before assuming
the body is the shape you expect; skipping that check is the single most
common mistake in beginner external-API integration code.

---

**Q: A downstream service starts returning `429 Too Many Requests`. What's the correct response, versus what a naive retry loop does wrong?**

Correct: read the `Retry-After` header (if present) and back off for that
duration before trying again — you're being told exactly how long to
wait. A naive retry loop that immediately retries on any non-2xx makes the
rate-limiting worse, potentially getting your client blocked entirely.
429 needs different handling than a generic 5xx retry.

---

**Q: Why prefer exponential backoff with jitter over a fixed retry delay when calling a struggling downstream API?**

A fixed delay (e.g. every client retries exactly 500ms later) synchronizes
retries from many concurrent callers into repeated bursts hitting the
already-struggling service at the same moments — the same thundering-herd
problem covered in the cache note. Exponential backoff spreads retries
out over increasing intervals, and jitter desynchronizes different
clients' retry timing so they don't all pile on at once.

---

**Q: When would you add a circuit breaker on top of retries, instead of just retrying more aggressively?**

When the downstream outage is sustained, not transient — retries (even
with backoff) still mean every request pays the cost of attempting and
timing out against a service that's clearly down. A circuit breaker trips
after enough consecutive failures and starts failing fast (no network
call at all) for a cooldown window, protecting your own service's latency
and resource usage during someone else's outage, then automatically tests
recovery afterward.

---

**Q: How do you unit-test what your code does when an external API times out, without actually waiting for a real timeout in your test suite?**

Point your code at a local `httptest.NewServer` whose handler deliberately
sleeps longer than your configured timeout (using a short timeout in the
test, e.g. 50ms, not your real production value), and assert your code's
error-handling path behaves correctly — without needing a real flaky
external dependency or a slow test run.

---

**Q: You're calling an external exchange-rate API on every request to convert prices, and it's both slow and rate-limited. What's the fix?**

Cache the result (cache-aside pattern) with a TTL appropriate to how often
the rate actually needs to be fresh — e.g. 5 minutes for a currency rate
that doesn't need per-request accuracy. This directly reduces both your
exposure to the API's latency and your risk of hitting its rate limit,
and it's the same pattern as any other expensive-external-call caching
scenario.

---

**Q: A client cancels their request (closes the connection) while your handler is mid-way through calling a slow external API. What happens by default, and how do you fix it?**

By default, nothing stops the outgoing call — your handler keeps waiting
on the external API and doing pointless work for a response nobody will
receive. Propagate the incoming request's context (`c.Ctx.Request.Context()`)
into the outgoing call via `http.NewRequestWithContext`, so cancellation
upstream cancels the downstream call too, freeing up resources
immediately instead of waiting out the full timeout.
