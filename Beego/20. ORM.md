# Beego ORM & Database

Reference notes on `github.com/beego/beego/v2/client/orm`, the ORM package
that ships with the Beego web framework for Go. <cite index="6-1">It's heavily influenced by Django ORM and SQLAlchemy.</cite>

---

# Part 1 — Beginner

## 1. Overview

<cite index="2-1">Beego's ORM package provides ORM support for MySQL, PostgreSQL, and SQLite</cite> (TiDB and Oracle are also supported as driver types). <cite index="1-1">As of v2.x, the ORM instance is stateless, which makes it thread-safe.</cite>

You get three ways to talk to your database, in increasing order of control:

1. **ORM model methods** — `Insert`, `Update`, `Read`, `Delete` on structs. Best for simple CRUD.
2. **QuerySeter** — a fluent, chainable query builder for filters, joins, ordering, pagination.
3. **Raw SQL** — full raw queries when you need complete control, via `Raw()`.

<cite index="18-1">There's also a separate QueryBuilder API — an alternative to the ORM for constructing complex SQL (subqueries, multi-joins) without writing raw SQL strings by hand.</cite>

---

## 2. Installation

```bash
go get github.com/beego/beego/v2/client/orm
```

You'll also need a database driver, imported blank so it registers itself:

```go
import (
    "github.com/beego/beego/v2/client/orm"
    _ "github.com/go-sql-driver/mysql"   // MySQL
    // _ "github.com/lib/pq"             // PostgreSQL
    // _ "github.com/mattn/go-sqlite3"   // SQLite
)
```

## 3. Registering a database

```go
package main

import (
    "fmt"

    "github.com/beego/beego/v2/client/orm"
    _ "github.com/go-sql-driver/mysql"
)

func init() {
    orm.RegisterDriver("mysql", orm.DRMySQL)
    orm.RegisterDataBase("default", "mysql", "root:root@/my_db?charset=utf8")
}
```

<cite index="2-1">`RegisterDataBase(aliasName, driverName, dataSource string, params ...int)` registers a database under an alias</cite> — `"default"` is the alias used automatically when you don't specify one. You can register multiple databases under different aliases (e.g. `"default"`, `"readonly"`, `"analytics"`) and route queries to specific ones via `QueryTable` / alias-aware calls.

## 4. Defining models

```go
type User struct {
    Id   int    `orm:"auto"`
    Name string `orm:"size(100)"`
}

func init() {
    orm.RegisterModel(new(User))
}
```

<cite index="3-1">Models are registered in `init()`, and `RegisterModel` can register multiple models at once</cite>: <cite index="1-1">`orm.RegisterModel(new(User), new(Profile), new(Post))`.</cite>

**Common struct tags:**

| Tag                | Meaning                                      |
|--------------------|-----------------------------------------------|
| `orm:"auto"`       | Auto-incrementing primary key                |
| `orm:"size(100)"`  | Column size (e.g. `VARCHAR(100)`)            |
| `orm:"pk"`         | Explicit primary key (for non-auto keys)     |
| `orm:"unique"`     | Unique constraint                            |
| `orm:"null"`       | Allow NULL                                   |
| `orm:"default(x)"` | Default value                                |
| `orm:"index"`      | Create an index on this column               |

## 5. Basic CRUD

```go
package main

import (
    "fmt"

    "github.com/beego/beego/v2/client/orm"
    _ "github.com/go-sql-driver/mysql"
)

type User struct {
    Id   int    `orm:"auto"`
    Name string `orm:"size(100)"`
}

func init() {
    orm.RegisterDriver("mysql", orm.DRMySQL)
    orm.RegisterDataBase("default", "mysql", "root:root@/my_db?charset=utf8", 30)
    orm.RegisterModel(new(User))
}

func main() {
    o := orm.NewOrm()
    user := User{Name: "slene"}

    // insert
    id, err := o.Insert(&user)

    // update
    user.Name = "astaxie"
    num, err := o.Update(&user)

    // read one (by primary key already set on struct)
    u := User{Id: user.Id}
    err = o.Read(&u)

    // delete
    num, err = o.Delete(&u)

    fmt.Println(id, num, err)
}
```

<cite index="2-1">This mirrors the standard flow: create an `Ormer` with `orm.NewOrm()`, then call `Insert`, `Update`, `Read`, `Delete` on it.</cite>

## 6. Auto-creating tables

<cite index="1-1">You can have Beego automatically create your database tables</cite>, either via the `bee` CLI tool, or programmatically:

```go
name := "default"
force := true   // drop table and re-create
verbose := true // print log

err := orm.RunSyncdb(name, force, verbose)
if err != nil {
    fmt.Println(err)
}
```

<cite index="1-1">After the initial run, switch `force` and `verbose` back to `false` — Beego's default behavior is to add additional columns when the model changes, not to drop/recreate.</cite>

> ⚠️ Never leave `force := true` in a production build — it drops the table every time the app starts.

---

## 7. QuerySeter — the fluent query API

<cite index="14-1">ORM uses QuerySeter to organize queries; every method that returns a QuerySeter gives you a new QuerySeter object</cite> (so you can chain safely without mutating shared state).

```go
o := orm.NewOrm()
var qs orm.QuerySeter
qs = o.QueryTable("user") // panics if the table can't be found
```

**Filtering:**

```go
// WHERE UserName = 'slene'
qs.Filter("UserName", "slene")

// Follows a relation: left outer join profile ... WHERE t1.age == 28
qs.Filter("profile__Age", 28)

// Time comparison
qs.Filter("created", time.Now())
```

<cite index="13-1">`FilterRaw` lets you drop in a raw SQL condition when `Filter` isn't expressive enough</cite>, e.g. `qs.FilterRaw("user_id IN (SELECT id FROM profile WHERE age>=18)")`. `Exclude` works the same way as `Filter` but negates the condition (NOT).

**Common chainable methods:** `Filter`, `Exclude`, `SetCond`, `OrderBy`, `Limit`, `Offset`, `RelatedSel` (eager-load relations), `Count`, `Exist`, `All`, `One`, `Values`, `ValuesList`, `ValuesFlat`.

## 8. Raw SQL

When you need full control, drop down to raw SQL:

```go
o := orm.NewOrm()
var r orm.RawSeter
r = o.Raw("UPDATE user SET name = ? WHERE name = ?", "testing", "slene")
res, err := r.Exec()
```

<cite index="11-1">`RawSeter` (created via `Ormer.Raw`) supports `Exec()` to run and get a result, `QueryRow` to map a single row into variables, and `QueryRows` to map multiple rows into slices.</cite>

```go
var name string
var id int
o.Raw("SELECT id, name FROM user WHERE id = ?", 1).QueryRow(&id, &name)

var ids []int
var names []string
num, err := o.Raw("SELECT id, name FROM user").QueryRows(&ids, &names)
```

Always use `?` placeholders with args passed separately — never string-concatenate user input into SQL (see the security section in Part 2).

## 9. Relationships

```go
type User struct {
    Id      int
    Name    string
    Profile *Profile `orm:"rel(one)"`     // one-to-one
}

type Profile struct {
    Id   int
    Age  int16
    User *User `orm:"reverse(one)"`        // reverse side (optional)
}

func init() {
    orm.RegisterModel(new(User), new(Profile))
}
```

Common relation tags: `rel(one)` (FK, one-to-one/many-to-one), `rel(fk)` (explicit foreign key/one-to-many), `rel(m2m)` (many-to-many), `reverse(one)` / `reverse(many)` for the inverse side.

```go
profile := new(Profile)
profile.Age = 30

user := new(User)
user.Profile = profile
user.Name = "slene"

o.Insert(profile)
o.Insert(user)
```

# Part 2 — Advanced

## 11. Transactions

```go
o := orm.NewOrm()
err := o.DoTx(func(ctx context.Context, txOrm orm.TxOrmer) error {
    if _, err := txOrm.Insert(&user); err != nil {
        return err // triggers rollback
    }
    if _, err := txOrm.Insert(&profile); err != nil {
        return err
    }
    return nil // triggers commit
})
```

`DoTx` is the recommended pattern — it wraps `Begin`/`Commit`/`Rollback` for you and rolls back automatically if your function returns an error or panics. The manual, lower-level equivalent:

```go
o := orm.NewOrm()
to, err := o.Begin()
if err != nil {
    // handle
}

if _, err := to.Insert(&user); err != nil {
    to.Rollback()
    return err
}

if err := to.Commit(); err != nil {
    return err
}
```

<cite index="16-1">Note: `TxOrm` is a stateful object — once a transaction ends, you should drop it rather than reuse it.</cite> <cite index="16-1">Also note that Beego deliberately removed the old `Using` method for switching DB aliases mid-query, since it was a common source of concurrency bugs — prefer scoping your alias per-call instead.</cite>

---

## 12. QueryBuilder — for complex SQL

<cite index="18-1">QueryBuilder is a separate API that provides fluent construction of SQL queries — it's positioned as an alternative to ORM: ORM is best for simple CRUD, QueryBuilder is best for complex queries with subqueries and multi-joins.</cite>

```go
type User struct {
    Name string
    Age  int
}
var users []User

qb, _ := orm.NewQueryBuilder("mysql")
qb.Select("user.name", "profile.age").
    From("user").
    InnerJoin("profile").On("user.id_user = profile.fk_user").
    Where("age > ?").
    OrderBy("name").Desc().
    Limit(10).Offset(0)

sql := qb.String()
o := orm.NewOrm()
o.Raw(sql, 20).QueryRows(&users)
```

<cite index="18-1">You build the query step by step (Select → From → Join → Where → OrderBy → Limit/Offset), export it as a raw SQL string with `.String()`, then execute it via `o.Raw(sql, args...)`.</cite> This gives you SQL-level expressiveness while keeping placeholder-based parameterization for the actual argument values.

## 13. Security: SQL injection

The ORM's `Filter`/`Exclude` and parameterized `Raw(sql, args...)` calls are safe by
design — arguments are passed through the driver's placeholder mechanism, not
string-concatenated.

**Danger zones to watch:**

- `FilterRaw` and `QueryBuilder`'s `.Where("age > ?")` still expect you to use
  `?` placeholders and pass values as args — if you instead build the WHERE
  clause by concatenating user input directly into the string, you've
  reintroduced SQL injection despite using the "safe" API.
- Table/column names can't be parameterized by the driver (only values can),
  so if you ever build a dynamic table/column name from user input, validate
  it against an allowlist rather than trusting it directly.
- <cite index="7-1">Beego has had real security advisories in the past (e.g. GO-2025-3585, a reflected/stored XSS issue in `RenderForm()`)</cite> — unrelated to ORM directly, but a reminder to keep Beego dependencies current and check the Go vulnerability database (`govulncheck`) periodically for your specific version.

**Rule of thumb:** anywhere you see a `?` in the docs, that's the only safe place for user-supplied values. Never `fmt.Sprintf` a value directly into a SQL string.

## 14. Connection pooling & performance

`RegisterDataBase` accepts optional int params for pool tuning:

```go
orm.RegisterDataBase("default", "mysql", dsn, maxIdleConns, maxOpenConns)
```

- **maxIdleConns** — connections kept idle/ready for reuse.
- **maxOpenConns** — hard cap on total open connections to the DB.

Under-provisioning `maxOpenConns` causes request queuing/latency spikes under
load; over-provisioning can exhaust your DB server's own connection limit,
especially with multiple app instances. Size this relative to
`(DB max_connections) / (number of app instances)`, leaving headroom for
other services sharing the DB.

**Other performance notes:**

- `RelatedSel()` (eager loading) avoids N+1 query problems when reading a
  model together with its related models — use it instead of looping and
  issuing a separate query per row.
- `Values`/`ValuesList`/`ValuesFlat` are cheaper than full model hydration
  when you only need a few columns, since they skip reflecting into full
  struct instances.
- For bulk inserts, look for `InsertMulti` (batch insert) rather than
  looping `Insert` calls — far fewer round trips.
- `DefaultRowsLimit` — the ORM applies a default row limit to `All()`
  queries unless you explicitly set `Limit(-1)` or a specific value; be
  aware of this so you don't get silently truncated results on large
  tables.

## 15. Debugging & query logging

```go
orm.Debug = true
```

<cite index="4-1">With `Debug` enabled, Beego logs every query it executes along with timing</cite>, e.g. an `INSERT INTO` statement with its execution time in milliseconds — invaluable for catching N+1 problems and slow queries during development. Turn this off in production (it adds overhead and can leak query data into logs).

For structured logging, `orm.NewLog(out io.Writer)` lets you redirect ORM's debug/query logs to your own logger sink instead of stdout.

## 16. Testing strategies

- **Use a real ephemeral DB, not mocks, for ORM tests.** Because the ORM
  generates real SQL against the registered driver, mocking the `Ormer`
  interface tends to be brittle and low-value — prefer spinning up a real
  SQLite in-memory DB or a disposable Postgres/MySQL container
  (e.g. via `testcontainers-go`) for integration tests.
- **SQLite in-memory for fast unit tests:**

```go
orm.RegisterDriver("sqlite3", orm.DRSqlite)
orm.RegisterDataBase("default", "sqlite3", ":memory:")
orm.RegisterModel(new(User))
orm.RunSyncdb("default", true, false)
```

  This gives you a throwaway schema per test run with no external
  dependency, at the cost of not catching MySQL/Postgres-specific SQL
  dialect issues.
- **Wrap each test in a transaction and roll it back** at the end, so tests
  don't leak state into each other when sharing a single test database.

---

## 17. Custom fields & hooks

- **Custom field types** — implement the `Fielder` interface (`SetRaw`,
  `RawValue`, `FieldType`, etc.) if you need a Go type that doesn't map
  cleanly onto SQL column types (e.g. a custom `Money` or `JSON` type).
- **`TableName()` hook** — implement this on your model to override the
  default (pluralized/snake_cased) table name:

```go
func (u *User) TableName() string {
    return "app_users"
}
```

- **`TableEngine()` / `TableIndex()` / `TableUnique()`** — optional hooks to
  control storage engine (MySQL `InnoDB` etc.), composite indexes, and
  composite unique constraints at table-creation time via `RunSyncdb`.

## 18. Multiple databases & read/write splitting

```go
orm.RegisterDataBase("default", "mysql", primaryDSN)
orm.RegisterDataBase("readonly", "mysql", replicaDSN)
```

```go
o := orm.NewOrm()
qs := o.QueryTable("user") // uses "default" alias
```

To route a specific query to a non-default alias, use the alias-aware
variant available for that call rather than the removed `Using()` method
(see §11) — check the exact method name for your installed version, since
this surface has shifted across v2 releases. This pattern is commonly used
for primary/replica read-write splitting: writes go to `"default"`
(primary), read-heavy reporting queries go to `"readonly"` (replica).

# Part 3 — Use-Case Q&A

The kind of questions a code review, interview, or real design decision
would actually ask — with the reasoning, not just the answer.

---

**Q: ORM, QuerySeter, QueryBuilder, or raw SQL — how do you actually decide?**

- **ORM methods** (`Insert`/`Update`/`Read`/`Delete`) — single-row CRUD on
  one model. Fastest to write, least flexible.
- **QuerySeter** — multi-row reads with filters/ordering/pagination that
  map cleanly onto one table (plus simple relation joins via `__`). This is
  your default for "list users where X, ordered by Y, paginated."
- **QueryBuilder** — you need real SQL shape: multiple joins, subqueries,
  aggregate functions, `GROUP BY`/`HAVING`. You still get placeholder
  safety, but you're describing the query structurally instead of via
  Django-style filter chains.
- **Raw SQL (`o.Raw`)** — vendor-specific SQL, complex CTEs, window
  functions, or anything QueryBuilder can't express. Last resort, but not
  a bad one — it's still safe as long as you use `?` placeholders.

Rule of thumb: start with QuerySeter; reach for QueryBuilder when you catch
yourself fighting the filter API for a join-heavy report query; reach for
raw SQL when you need a DB-specific feature.

---

**Q: You have a page listing 50 users, each showing their profile info. What's the naive mistake, and how do you avoid it?**

The naive version loops over 50 users and calls `o.Read(&profile)` once
per user — that's 51 queries (1 + N), the classic **N+1 problem**. Fix it
with `RelatedSel()` to eager-load the relation in a single joined query:

```go
var users []*User
o.QueryTable("user").RelatedSel("Profile").All(&users)
```

One query instead of 51. This is the single most common Beego ORM
performance bug in real codebases.

---

**Q: Two inserts need to succeed or fail together — how do you structure that?**

Wrap them in `DoTx`, not two separate `Insert` calls:

```go
err := o.DoTx(func(ctx context.Context, txOrm orm.TxOrmer) error {
    if _, err := txOrm.Insert(&order); err != nil {
        return err
    }
    if _, err := txOrm.Insert(&payment); err != nil {
        return err
    }
    return nil
})
```

If `payment` insert fails, `order` insert is rolled back too — `DoTx`
handles commit/rollback automatically based on the returned error. Without
a transaction, a mid-way failure leaves an orphaned `order` row with no
matching `payment`.

---

**Q: Your app is randomly getting "too many connections" errors from MySQL under load — where do you look first?**

`RegisterDataBase`'s `maxOpenConns` param (or its absence — an unbounded
default). Check it against `(DB's max_connections) / (number of running
app instances)`. This is a connection-pool sizing problem, not a code bug
— multiply it out: 10 app instances × an unbounded pool can easily blow
past MySQL's default 151 connection limit.

---

**Q: A user-facing search box lets people filter by name. What's the safe way to build that query?**

Use `Filter`, not string concatenation:

```go
qs := o.QueryTable("user")
if name != "" {
    qs = qs.Filter("Name__icontains", name)
}
```

Never do `qs.FilterRaw(fmt.Sprintf("name LIKE '%%%s%%'", name))` — that's
SQL injection even though it's routed through the "ORM." `FilterRaw` and
`QueryBuilder.Where()` are only safe when the user-controlled part is
passed as a `?` arg, not interpolated into the SQL string itself.

---

**Q: How would you migrate an existing production table without downtime, given `RunSyncdb`'s force-drop behavior?**

Don't use `force := true` on a live table — that drops and recreates it,
losing data. `RunSyncdb(name, false, verbose)` will *add* new columns for
model changes but won't handle column drops, renames, or type changes
safely. For real production schema changes, use a dedicated migration tool
(the `bee` CLI's migration commands, or `golang-migrate`/`goose`) that
generates versioned, reviewable SQL migration files instead of relying on
ORM auto-sync.

---

**Q: When would you deliberately choose raw SQL / `TxDB` over the ORM entirely for a specific piece of logic?**

- Bulk analytical queries (large aggregations, reporting) where ORM
  overhead (reflection, struct hydration) is measurably slower than a
  hand-tuned query.
  Batch jobs with `InsertMulti` or raw multi-row `INSERT ... VALUES (...),
  (...)` for performance.
- DB-specific features the ORM doesn't model (e.g. Postgres `JSONB`
  operators, MySQL `ON DUPLICATE KEY UPDATE`, window functions).
- When you need the underlying `*sql.DB`/`*sql.Tx` directly to interop with
  another library that expects the standard `database/sql` types — `orm`
  exposes `TxDB` for exactly this kind of interop.

---

**Q: How do you unit-test a service function that does an ORM read, without hitting a real database in CI?**

Prefer a real, disposable database over mocking the `Ormer` interface —
mocking ORM internals is brittle because you end up re-implementing query
semantics in your mock. Two practical options:

1. **SQLite in-memory** (`:memory:`) — fast, zero external dependency,
   good for pure logic tests. Downside: won't catch MySQL/Postgres-only SQL
   dialect issues (e.g. `FilterRaw` with vendor-specific syntax).
2. **Real DB in a container** (`testcontainers-go`) for integration tests
   that need to be dialect-accurate — slower, but catches real bugs SQLite
   would miss.

Use SQLite for fast feedback in most unit tests; reserve containerized
Postgres/MySQL for integration/CI suites that specifically need dialect
fidelity.

---

**Q: What's the difference between `Filter("profile__Age", 28)` and manually joining tables with QueryBuilder?**

`Filter("profile__Age", 28)` auto-generates a join based on the registered
relation (`rel(one)`/`rel(fk)` on your model) — Beego infers the join
condition from the model definition. QueryBuilder's `.InnerJoin(...).On(...)`
requires you to spell out the join condition yourself, but works for joins
that aren't modeled as ORM relations at all (e.g. joining on a computed
key, or joining to a table that isn't a registered model). Use `Filter`'s
relation traversal for anything already modeled as a relationship; use
QueryBuilder when the join isn't naturally expressible as a model relation.
