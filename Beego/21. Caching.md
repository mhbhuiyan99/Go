# Beego Cache Module — Notes

Reference notes on `github.com/beego/beego/v2/client/cache`, the caching package
that ships with the Beego web framework for Go.

---

## 1. Overview

Beego's cache module handles temporary, in-memory-or-external key/value storage.
It's modeled after Go's `database/sql` package: you get one common `Cache`
interface, and you plug in whichever backend ("adapter") you need without
changing your application code.

**Supported providers (adapters):**

| Provider  | Use case                                      |
|-----------|------------------------------------------------|
| `memory`  | Fast, in-process cache. Data lost on restart.  |
| `file`    | Cache persisted to disk as files.              |
| `memcache`| External Memcached server(s).                  |
| `redis`   | External Redis server(s).                      |

Because everything implements the same `Cache` interface, swapping `memory`
for `redis` in production is usually a one-line config change.

---

## 2. Installation

```bash
go get github.com/beego/beego/v2/client/cache
```

For memcache or redis, you need the adapter subpackage too:

```bash
# Memcache
go get -u github.com/beego/beego/v2/client/cache/memcache

# Redis
go get -u github.com/beego/beego/v2/client/cache/redis
```

And blank-import the adapter so it registers itself:

```go
import (
    "github.com/beego/beego/v2/client/cache"
    _ "github.com/beego/beego/v2/client/cache/memcache"
    _ "github.com/beego/beego/v2/client/cache/redis"
)
```

---

## 3. The `Cache` interface

Every provider implements this interface, so this is really the whole API
surface you need to learn:

```go
type Cache interface {
    // Get a cached value by key.
    Get(ctx context.Context, key string) (interface{}, error)

    // GetMulti is a batch version of Get.
    GetMulti(ctx context.Context, keys []string) ([]interface{}, error)

    // Put a value with an expiration time.
    Put(ctx context.Context, key string, val interface{}, timeout time.Duration) error

    // Delete a cached value by key.
    Delete(ctx context.Context, key string) error

    // Incr increments a cached int value by key (counter).
    Incr(ctx context.Context, key string) error

    // Decr decrements a cached int value by key (counter).
    Decr(ctx context.Context, key string) error

    // IsExist checks if a cached value exists.
    IsExist(ctx context.Context, key string) (bool, error)

    // ClearAll clears the entire cache.
    ClearAll(ctx context.Context) error
}
```

> ⚠️ **Version note:** Older Beego (`astaxie/beego`, pre-v2) used the same
> method names but *without* the `context.Context` first argument. If you
> copy examples from old blog posts or Stack Overflow answers, add `ctx` as
> the first parameter — the modern `v2` module requires it everywhere.

## 4. Basic usage

```go
package main

import (
    "context"
    "fmt"
    "time"

    "github.com/beego/beego/v2/client/cache"
)

func main() {
    ctx := context.Background()

    // Create a memory cache, GC interval = 60s
    bm, err := cache.NewCache("memory", `{"interval":60}`)
    if err != nil {
        panic(err)
    }

    // Set a value, expires in 10 seconds
    _ = bm.Put(ctx, "astaxie", 1, 10*time.Second)

    // Read it back
    if v, err := bm.Get(ctx, "astaxie"); err == nil {
        fmt.Println("value:", v)
    }

    // Check existence
    exists, _ := bm.IsExist(ctx, "astaxie")
    fmt.Println("exists:", exists)

    // Delete
    _ = bm.Delete(ctx, "astaxie")
}
```

## 5. Provider configuration

Each provider is configured via a JSON string passed to `cache.NewCache(name, config)`.

### memory

```json
{"interval": 60}
```

- `interval` — garbage-collection interval in seconds. The cache scans and
  purges expired keys every `interval` seconds.

### file

```json
{
  "CachePath":        "./cache",
  "FileSuffix":       ".cache",
  "DirectoryLevel":    "2",
  "EmbedExpiry":       "0"
}
```

- `CachePath` — root directory where cache files are written.
- `FileSuffix` — extension appended to cache files.
- `DirectoryLevel` — how many nested subdirectories to spread files across
  (avoids too many files in one directory).
- `EmbedExpiry` — whether expiry metadata is embedded in the file.

### memcache

```json
{"conn": "127.0.0.1:11211"}
```

- `conn` — one or more memcache server addresses (comma-separated for
  multiple servers).
- Requires: `go get github.com/beego/beego/v2/client/cache/memcache`

### redis

```json
{"conn": "127.0.0.1:6379"}
```

- `conn` — Redis server address. Additional options (password, DB index)
  can be supplied depending on adapter version — check the adapter's
  source/docs for the exact key names in the version you're using.
- Requires: `go get github.com/beego/beego/v2/client/cache/redis`

## 6. Common patterns

### Cache-aside (lazy loading)

The most common pattern — check cache first, fall back to the real data
source, then populate the cache:

```go
func getUser(ctx context.Context, bm cache.Cache, id string) (*User, error) {
    key := "user:" + id

    if v, err := bm.Get(ctx, key); err == nil && v != nil {
        if u, ok := v.(*User); ok {
            return u, nil // cache hit
        }
    }

    // cache miss — load from DB
    user, err := loadUserFromDB(id)
    if err != nil {
        return nil, err
    }

    _ = bm.Put(ctx, key, user, 5*time.Minute)
    return user, nil
}
```

### Counters

```go
_ = bm.Put(ctx, "views", 0, 0) // 0 timeout = no expiry (provider-dependent)
_ = bm.Incr(ctx, "views")
_ = bm.Incr(ctx, "views")
v, _ := bm.Get(ctx, "views") // 2
```

### Batch reads

```go
keys := []string{"user:1", "user:2", "user:3"}
values, err := bm.GetMulti(ctx, keys)
```

## 7. Gotchas / things worth knowing

1. **Type assertions on `Get`** — `Get` returns `interface{}`, so you must
   type-assert the result. If you stored a struct pointer, retrieve it as
   the same pointer type.
2. **Zero timeout behavior differs by provider** — some treat `0` as "never
   expires," others may treat it differently. Check the adapter you're
   using if this matters.
3. **MD5 cache-key collisions (file provider)** — there's a known advisory
   (`GO-2024-3331`) about MD5 being used for cache key filenames in older
   Beego versions, which can theoretically cause collisions. Keep your
   Beego version up to date.
4. **Context is mandatory in v2** — forgetting `ctx` as the first arg is the
   #1 migration bug when porting old `astaxie/beego` code to `beego/beego/v2`.
5. **`beego-cache` standalone repo** — `github.com/beego/beego-cache` is an
   independently versioned extraction of this same module, useful if you
   want just the cache package without the rest of the framework.

## 9. Writing a custom cache adapter

Since every provider just implements the `Cache` interface, you can plug in
your own backend — e.g. a Postgres table, DynamoDB, or an in-house service.

```go
package mycache

import (
    "context"
    "time"

    "github.com/beego/beego/v2/client/cache"
)

type DBCache struct {
    // your own fields — db handle, table name, etc.
}

func (c *DBCache) Get(ctx context.Context, key string) (interface{}, error) {
    // look up row by key, check expiry column
    return nil, nil
}

func (c *DBCache) GetMulti(ctx context.Context, keys []string) ([]interface{}, error) {
    // batch lookup
    return nil, nil
}

func (c *DBCache) Put(ctx context.Context, key string, val interface{}, timeout time.Duration) error {
    // upsert row with expiry = now + timeout
    return nil
}

func (c *DBCache) Delete(ctx context.Context, key string) error { return nil }
func (c *DBCache) Incr(ctx context.Context, key string) error   { return nil }
func (c *DBCache) Decr(ctx context.Context, key string) error   { return nil }
func (c *DBCache) IsExist(ctx context.Context, key string) (bool, error) { return false, nil }
func (c *DBCache) ClearAll(ctx context.Context) error { return nil }

// StartAndGC is called by cache.NewCache — this is where you parse the
// JSON config string and initialize your backend.
func (c *DBCache) StartAndGC(config string) error {
    // parse `config` (JSON), open DB connection, etc.
    return nil
}

// Register your adapter under a name, typically in an init().
func init() {
    cache.Register("dbcache", func() cache.Cache { return &DBCache{} })
}
```

Then use it exactly like a built-in provider:

```go
import _ "yourmodule/mycache"

bm, err := cache.NewCache("dbcache", `{"table":"cache_kv"}`)
```

This is the same mechanism the `memcache` and `redis` adapters use — they're
not special-cased in the core package.

## 10. Concurrency safety

- **`memory` provider** is safe for concurrent use — it wraps its internal
  map with a mutex. You can call `Get`/`Put` from many goroutines without
  extra locking on your side.
- **`Incr`/`Decr`** are atomic *within a single provider instance*, but if
  you're running multiple app instances against `memory` (which is
  per-process), counters won't be shared — you need `redis` or `memcache`
  for a distributed counter.
- **`file` provider** — file writes are not always atomic across concurrent
  writers; heavy concurrent write load can cause races or partial writes
  depending on OS/filesystem. Avoid `file` for high-write-throughput
  counters; prefer it for low-churn, read-mostly caching.
- **`redis`/`memcache`** — atomicity of `Incr`/`Decr` is guaranteed by the
  server itself (Redis `INCR`, Memcached `incr` are atomic commands), so
  these are the right choice for distributed counters (e.g. rate limiting).

**Rule of thumb:** if multiple processes/instances need to see the same
cache state, don't use `memory` — it's local to the process.

## 11. Cache stampede (thundering herd) protection

**The problem:** a hot key expires, and dozens of concurrent requests all
miss the cache at once and hit your database simultaneously.

**Mitigation patterns:**

1. **Singleflight** — dedupe concurrent loads for the same key so only one
   goroutine actually queries the DB; others wait for its result.

```go
import "golang.org/x/sync/singleflight"

var g singleflight.Group

func getUser(ctx context.Context, bm cache.Cache, id string) (*User, error) {
    key := "user:" + id

    if v, err := bm.Get(ctx, key); err == nil && v != nil {
        return v.(*User), nil
    }

    v, err, _ := g.Do(key, func() (interface{}, error) {
        user, err := loadUserFromDB(id)
        if err != nil {
            return nil, err
        }
        _ = bm.Put(ctx, key, user, 5*time.Minute)
        return user, nil
    })
    if err != nil {
        return nil, err
    }
    return v.(*User), nil
}
```

2. **Jittered TTLs** — instead of a fixed `5*time.Minute` for every key, add
   random jitter (`5*time.Minute + time.Duration(rand.Intn(60))*time.Second`)
   so keys don't all expire at the exact same moment.

3. **Early refresh** — refresh the cache slightly before actual expiry
   (background refresh) so requests basically never see a cold cache for
   hot keys.

4. **Stale-while-revalidate** — serve the (slightly) stale value
   immediately while asynchronously refreshing it in the background.

Beego's cache module doesn't give you these for free — you build them on
top of `Get`/`Put`, typically with `singleflight` + jittered TTL as the
minimum viable protection for hot keys.

## 12. Using cache inside a Beego controller

Typical pattern: initialize the cache once (e.g. package-level var, or via
dependency injection), then use it inside your controller's action methods.

```go
package controllers

import (
    "context"
    "time"

    "github.com/beego/beego/v2/client/cache"
    beego "github.com/beego/beego/v2/server/web"
)

var bm cache.Cache

func init() {
    var err error
    bm, err = cache.NewCache("memory", `{"interval":60}`)
    if err != nil {
        panic(err)
    }
}

type ProductController struct {
    beego.Controller
}

func (c *ProductController) Get() {
    ctx := context.Background()
    id := c.Ctx.Input.Param(":id")
    key := "product:" + id

    if v, err := bm.Get(ctx, key); err == nil && v != nil {
        c.Data["json"] = v
        c.ServeJSON()
        return
    }

    product, err := loadProductFromDB(id)
    if err != nil {
        c.Ctx.Output.SetStatus(404)
        return
    }

    _ = bm.Put(ctx, key, product, 2*time.Minute)
    c.Data["json"] = product
    c.ServeJSON()
}
```

**Response caching as middleware/filter:** for read-heavy GET endpoints, you
can wrap this pattern into a Beego `FilterFunc` that caches the full
serialized response body keyed by URL + query params, so you don't have to
repeat the cache-check boilerplate in every controller.

## 13. Error handling nuances by provider

| Provider  | Typical error sources                                   |
|-----------|-----------------------------------------------------------|
| `memory`  | Rare — mostly type-assertion errors on your side.        |
| `file`    | Filesystem permission errors, disk full, path not found. |
| `memcache`| Network timeouts, connection refused, server down.       |
| `redis`   | Network timeouts, auth failures, connection pool exhaustion. |

**Practical implications:**

- For `redis`/`memcache`, always treat cache errors as **non-fatal** — fall
  back to the source of truth (DB) rather than failing the request. A cache
  outage should degrade performance, not take your app down.

```go
v, err := bm.Get(ctx, key)
if err != nil {
    // log it, but don't return an error to the caller —
    // just fall through to the DB load
    log.Printf("cache get failed: %v", err)
}
```

- Wrap cache calls with a timeout via `context.WithTimeout` so a slow/hung
  redis connection doesn't stall your whole request:

```go
ctx, cancel := context.WithTimeout(ctx, 100*time.Millisecond)
defer cancel()
v, err := bm.Get(ctx, key)
```

## 14. Performance considerations

Rough guidance (actual numbers depend heavily on your hardware/network):

- **`memory`** — fastest by far (no serialization, no network). Limited by
  available RAM and is per-process (doesn't share state across instances or
  survive restarts).
- **`file`** — much slower than memory due to disk I/O; mainly useful for
  larger payloads you don't want in RAM, or simple single-instance apps
  without a Redis/Memcached dependency.
- **`redis`** — network round-trip cost, but shared across all app
  instances, supports rich data structures, persistence options, and pub/sub
  (useful for cache invalidation broadcast — see below).
- **`memcache`** — similar network cost to redis, generally simpler/leaner,
  good pure key-value performance, no persistence or advanced data types.

**When to choose what:**
- Single instance, non-critical data → `memory`
- Multiple instances / need shared state → `redis` or `memcache`
- Need persistence, atomic ops, pub/sub, or richer data types → `redis`
- Pure high-throughput KV with minimal overhead → `memcache`

## 15. Testing strategies

Because `Cache` is an interface, you can trivially mock it in unit tests
without spinning up real memory/redis backends.

```go
type mockCache struct {
    store map[string]interface{}
}

func newMockCache() *mockCache {
    return &mockCache{store: make(map[string]interface{})}
}

func (m *mockCache) Get(ctx context.Context, key string) (interface{}, error) {
    v, ok := m.store[key]
    if !ok {
        return nil, errors.New("not found")
    }
    return v, nil
}

func (m *mockCache) Put(ctx context.Context, key string, val interface{}, timeout time.Duration) error {
    m.store[key] = val
    return nil
}

// ... implement the rest of the interface similarly (can be no-ops for
// methods your test doesn't exercise)
```

For integration tests, spin up a real `memory` cache (cheap, no external
dependency) rather than mocking — it exercises the real code path with
minimal setup cost. Reserve actual redis/memcache instances (e.g. via
testcontainers) for tests that specifically need to verify
provider-specific behavior.

## 16. Advanced redis/memcache configuration

The bare `{"conn": "127.0.0.1:6379"}` shown in Part 1 works for local dev,
but production Redis/Memcache setups typically need more:

- **Auth / password** — check the specific adapter version's accepted JSON
  keys (varies by Beego version); commonly something like
  `{"conn": "127.0.0.1:6379", "password": "secret"}`.
- **DB index (redis)** — selecting a non-default Redis logical DB.
- **Connection pooling** — the adapters generally wrap a pooled client
  under the hood (e.g. `go-redis`), so you typically don't manage pooling
  yourself, but it's worth checking the adapter source if you need to tune
  pool size for high concurrency.
- **Cluster / sentinel mode** — for Redis Cluster or Sentinel setups, verify
  whether the bundled adapter supports it directly, or whether you should
  write a thin custom adapter (see §9) around `go-redis`'s cluster client
  for full control.
- **TLS** — similarly adapter-version-dependent; if not supported natively,
  a custom adapter wrapping a TLS-configured client is the reliable path.

**Practical tip:** for anything beyond basic single-node redis/memcache, it's
common in real production Beego apps to write a thin custom adapter (§9)
that wraps a fully-configured `go-redis` client, rather than relying on the
built-in adapter's JSON config surface — this gives you full control over
pooling, TLS, cluster mode, and retries.

## 17. Cache invalidation strategies

"There are only two hard things in Computer Science: cache invalidation and
naming things." Options, roughly in order of complexity:

1. **TTL-only** — simplest. Just let entries expire naturally. Fine when
   slightly-stale data is acceptable.
2. **Explicit invalidation on write** — when you update the underlying data
   (e.g. a DB row), immediately `bm.Delete(ctx, key)` or overwrite it with
   `bm.Put`. Requires discipline to catch every write path.
3. **Versioned keys** — instead of invalidating, change the key itself
   (e.g. `user:42:v3`) and bump the version on write. Old entries just
   expire naturally and are never read again. Avoids race conditions
   between "delete" and "someone re-populates the old value."
4. **Event-driven invalidation (pub/sub)** — with `redis`, you can publish
   an "invalidate" message on write, and have all app instances subscribe
   and evict the key from their local caches. Useful when you're layering a
   local `memory` cache in front of shared `redis` (two-tier caching) and
   need all instances to stay in sync.

**Two-tier caching** (memory + redis) is a common advanced pattern: check
local `memory` first (fastest), fall back to `redis` (shared), fall back to
DB. Requires an invalidation strategy (usually #4) so stale data doesn't
linger in the per-instance memory tier after a write.

# Part 3 — Use-Case Q&A

Real design-decision and interview-style questions, with the reasoning
behind each answer.

---

**Q: You're running 5 instances of your app behind a load balancer, and you want to cache DB reads. Why can't you just use the `memory` provider?**

`memory` is per-process — each of your 5 instances has its own isolated
cache. Two problems fall out of this: (1) low hit rate, since a request
hitting instance A can't benefit from a value already cached on instance B,
and (2) inconsistency — invalidating a key on instance A leaves it stale on
instances B–E. You need `redis` or `memcache` (shared, external) whenever
cache state needs to be consistent across multiple app processes.

---

**Q: A hot cache key just expired, and now 200 concurrent requests all miss at once and hammer your DB. How do you actually prevent this in code, not just in theory?**

Combine two things: `singleflight` to collapse the 200 concurrent DB loads
into 1 (the other 199 wait for that one result), and jittered TTLs so hot
keys don't all expire in the same instant in the first place. Neither one
alone is enough — jitter reduces how often stampedes happen, singleflight
caps the damage when one happens anyway.

---

**Q: `Get` returns `(interface{}, error)` — what's the actual failure mode if you skip the type assertion check?**

```go
v, _ := bm.Get(ctx, "user:1")
user := v.(*User) // panics if v is nil or a different type
```

If the key doesn't exist, `v` is `nil`, and `nil.(*User)` panics at
runtime — this is a real production crash pattern, not a theoretical one.
Always check both the error and use the two-value type assertion form:

```go
v, err := bm.Get(ctx, "user:1")
if err != nil || v == nil {
    // treat as cache miss, fall through to DB
}
user, ok := v.(*User)
if !ok {
    // treat as cache miss / corrupted entry, don't trust it
}
```

---

**Q: Redis is momentarily unreachable — what should happen to your app's requests?**

They should still succeed, just slower — cache failures must degrade
gracefully, never cascade into request failures. Treat `Get`/`Put` errors
from `redis`/`memcache` as non-fatal: log them, then fall through to the
DB as if it were a cache miss. Also wrap the cache call in a short
`context.WithTimeout` so a hung connection doesn't stall the whole request
waiting on a dead cache server.

---

**Q: You need a distributed rate limiter (e.g. 100 requests/min per user). Which provider, and why not `memory`?**

`redis`, because `Incr`/`Decr` need to be atomic *across all app
instances* sharing the same counter — a user's requests can land on any
instance behind the load balancer. `memory`'s `Incr` is only atomic within
one process, so a `memory`-based counter would undercount by a factor of
however many instances you're running, since each instance keeps its own
separate count.

---

**Q: When would you deliberately choose `file` over `memory` or `redis`?**

Rare in modern setups, but valid when: (1) you're running a single
instance with no Redis/Memcached infrastructure and still want cached data
to survive a process restart (memory doesn't persist; file does), or (2)
you're caching payloads too large to comfortably keep in RAM across many
keys. In most current production stacks, `redis` covers both persistence
and shared-state needs better, so `file` is mostly a fallback for
constrained, single-instance environments.

---

**Q: You update a user's profile in the DB. What's wrong with just letting the cached version expire naturally after its TTL?**

Between the write and the TTL expiry, every read serves stale data — for a
5-minute TTL, that's up to 5 minutes of an incorrect profile being shown,
which is often unacceptable (e.g. a user who just changed their
email seeing the old one). Explicit invalidation on write
(`bm.Delete(ctx, key)` right after the DB update succeeds) closes that
window immediately. TTL-only is fine for data where staleness is
genuinely tolerable (e.g. a "trending posts" list); it's the wrong choice
for anything a user just personally changed.

---

**Q: You're layering a local `memory` cache in front of shared `redis` (two-tier) for extra speed. What new problem does this introduce, and how do you solve it?**

Now you have N+1 places a value can live (N app instances' local memory,
plus redis), so an explicit `Delete` on one instance only clears that
instance's local copy and redis — the other instances' local memory tiers
are still stale. Solve it with pub/sub: on write, publish an invalidation
message on a Redis channel; every instance subscribes and evicts the key
from its own local `memory` tier on receipt. Without this, two-tier
caching silently reintroduces the staleness problem you were trying to
avoid.

---

**Q: How would you unit-test a function that reads from cache, without spinning up real Redis in CI?**

Since `Cache` is an interface, write a small in-memory mock (a
`map[string]interface{}` behind the same method set) and inject it in
tests — you don't need real redis/memcache infra for logic tests. Reserve
an actual `memory` provider instance (cheap, no external dependency) for
integration tests that want to exercise real TTL/expiry behavior; reserve
a real redis instance (e.g. via testcontainers) only for tests that
specifically verify redis-specific behavior like atomic `Incr` across
processes or pub/sub invalidation.
